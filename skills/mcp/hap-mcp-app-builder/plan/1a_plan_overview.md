## 一、 内部业务建模六步判断（思考后体现在方案中，不直接输出思考过程）

1. **识别业务场景类型**（可多类并存）：基础资料管理 / 审批流转 / 库存仓储 / 采购销售 / 借还租赁 / 生产加工 / 客户服务工单 / 项目任务协同 / 财务结算 / 运营分析。
2. **识别关键控制与异常机制**：状态流转 / 审批控制 / 时效约束 / 配额限制 / 批次与效期管理 / FIFO·FEFO / 冻结预留 / 部分执行 / 退回驳回作废 / 退货归还回冲 / 对账结算 / 盘盈盘亏差异 / 逾期损坏异常处理。
3. **规则结构化落地**：上述机制不得只停留在文字描述，必须落实为具体的工作表、自定义动作、自动化工作流、表单业务规则与统计看板。
4. **覆盖完整业务闭环**：发起 → 处理 → 审批执行 → 结果登记 → 异常处理 → 统计分析。
5. **补齐支撑对象**：除主业务对象外，按需补齐基础资料、过程明细、库存台账流水、异常记录与统计支撑表；不得为压缩表数量省略关键闭环对象。
6. **行业典型控制补足**：
   - **库存/仓储**：仓库、批次/效期、出入库流水、盘点、调拨、冻结预留；
   - **采购/销售**：订单、收发货、退货、对账结算、客商协同；
   - **借还/租赁**：借出、归还、逾期、续借、损坏遗失、在借状态控制；
   - **审批/工单/项目**：申请-审批-驳回重提留痕、受理-分派-回访-超时升级、计划-执行-变更-验收。

### 核心设计铁律
- **需求材料 1:1 保真**：用户给定 PRD 或字段清单时 100% 保留全部显式表、字段、选项与逻辑，严禁精简截断。
- **动作挂在操作发起方**：例如「发起借阅」挂在「图书」表，「确认归还」挂在「借阅记录」表。
- **自定义动作人工输入三态选型铁律（严禁错用 `triggerWorkflow` 导致后期返工！）**：
  - **物理底线**：**`triggerWorkflow`（直接触发工作流）点击后绝不弹出任何表单，无法收集操作人现场输入的读者、日期、数量、原因或异常类型！**
  - **需人工输入 + 在关联表产生新单据**（如在 `图书` 点「发起借阅」选借阅人/应还日期生成 `借阅记录`；在 `借阅记录` 点「登记损坏/遗失」填异常类型/赔偿额生成 `异常赔偿`）➔ **必须选 `createRelatedRecord`（新建关联记录）**，在源表显式规划指向目标表的 `Relation` 字段，提交后需扣库存/改状态则开启 `runWorkflowAfterSubmit: true`；
  - **需人工输入 + 修改当前记录字段**（如在 `借阅记录` 点「申请续借」填写新应还日期/续借原因；点「办理签到」填到场时间）➔ **必须选 `updateCurrentRecord`（填写当前记录）**，在当前表显式规划对应承接字段，提交后需联动则开启 `runWorkflowAfterSubmit: true`；
  - **100% 零人工输入**（所有数据均可由当前记录已有字段、点击人 `triggerUser`、系统当前时间或固定状态自动确定，如一键「确认归还」「提交审批」）➔ **才选 `triggerWorkflow`**。
- **严禁把审批结果拆成按钮**：禁止创建「审批通过」「审批驳回」自定义动作；统一使用发起动作或记录事件触发含审批块（`approval_block`）的工作流处理通过与驳回分支。

## 二、 方案总览 (`overview.md`) 标准输出结构

按以下章节直接输出方案总览（严禁加“系统/管理/平台/软件/后台”等笨重后缀，应用名控制在 2～8 字）：

```markdown
# 《应用名称》

# 1. 应用目标
说明解决的核心业务问题、适用场景与管理价值。

# 2. 关键设计思路
4～6 条，概括整体架构逻辑、关键业务控制规则与异常处理如何落到表、动作与工作流中。

# 3. 角色（Role）
- **角色名称**（外部角色标注“（外部）”）：1～2 句说明职责定位与主要参与方式。

# 4. 业务流程（Process & Information）
- **流程名称**：1～2 句说明前后衔接与业务闭环。

# 5. 应用内容（Content）

## 工作表
- **表名称**（子表标注“（子表 → 主表名）”）：1～2 句说明业务定位；若有自定义动作，列出动作名称。

（附 Mermaid erDiagram 展示核心表关联：实线 `--` 表示双向关联或主从子表，虚线 `..` 表示单向字典/主数据引用，表名加双引号）

## 自定义页面
- **页面名称**（`dashboard` 或 `workspace`）：1～2 句说明业务目的与适用角色。

## 自动化工作流
- **工作流名称**：触发方式 + 触发场景与业务结果。

## AI 助手
（按需规划，不强制）
- **助手名称**：1～2 句说明服务场景与数据范围。

## 导航分组
- **分组名称**：所含页面、工作表、AI 助手名称列表（子表归入其主表同一分组）。
```

## 三、 方案草稿修订连带分析（`APPLY` 修改未落地方案时执行）

当用户在物理构建前提出修改方案草稿时，严禁顺手重做未提及模块：

1. **四步连带推理**：
   - **理解意图**：定位修改的是工作表、自定义页面、AI 助手、角色、自定义动作还是工作流；
   - **扫描连带**：新增/删除/改名工作表时，同步检查 `roles` 权限引用、`workflows` 触发源与节点引用、`customActions` 所属表与目标表、`customPages` 图表数据源及其他表的 `Relation/SubTable` 引用；改 `triggerWorkflow` 动作时同步检查 `intentHints` 闭环；
   - **就地刷新总览**：`overview.md` 始终保持反映最新全貌的完整章节结构，就地改写受影响段落，**严禁在总览中添加“本轮变更记录/Changelog”章节**；
   - **闭环自检**：核对因果链（触发 → 状态变更 → 关联回写 → 留痕 → 通知）完整无孤立按钮。
2. **四大稳定性原则**：
   - **未要求修改的对象完全不动**（字段、描述、视图、顺序原样保留，严禁擅自“顺手优化”）；
   - **既有对象 `name` 持久化**（除非用户明确要求改名；改名须同步替换全部跨对象引用）；
   - **既有 `icon` / `color` 持久化**（不无故重挑既有元素的图标和颜色）；
   - **相对顺序持久化**（新增元素按主从拓扑或追加在对应分组末尾，不打乱原有顺序）。

## 四、 输出前六项闭环自检

1. 每个状态/分类视图的筛选条件在对应表的选项字段中均有匹配的选项值；
2. 时效性状态（如“已逾期”“临期”）均有配套定时/日期工作流自动标记；
3. 每个自定义动作的启用条件与业务流转前后状态闭环一致；
4. **每个自定义动作均已核对“是否需要操作人现场输入信息”**：凡需填写人员、日期、金额、类型或说明的动作，一律采用「新建关联记录」或「填写当前记录」（配合提交后触发工作流），严禁误设计为无输入框的「直接触发工作流」；
5. 所有工作表、自定义页面、AI 助手 100% 出现在导航分组中；
6. 核心业务角色均已按 `../references/hap-app-design-guide.md` 规划了匹配的仪表盘或工作台。
