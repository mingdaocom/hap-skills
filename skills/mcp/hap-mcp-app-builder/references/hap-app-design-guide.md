# HAP 应用设计指南

> 本文档覆盖 HAP 应用的**结构设计**（建哪些对象、如何组织）与**内容设计**（字段、视图、图表、工作流、自定义动作、打印模板的设计原则）。所有设计决策必须严格遵循本指南。

新建或整体重设计时应用相关完整性要求；局部修订只处理用户目标及必要依赖，保留范围外的既有设计，不因加载指南补做整套设计。复用有效事实与已确认选择，不为设计清单增加固定查询或确认；可执行范围、风险与授权沿用当前入口协议。

---

## 应用命名规范

应用名称代表整个系统的业务边界与专业度，应保持极致简洁、业务场景聚焦、富现代感，并遵循以下原则：

1. **剔除冗余后缀**：**严禁**使用“系统”、“平台”、“软件”、“工具”、“应用”、“表”、“系统后台”等传统而笨重的后缀。
   - ❌ 传统冗长：`SaaS 客户订阅与服务生命周期管理系统`、`重型设备维保管理平台`
   - ✅ 现代极简：`SaaS 客户订阅与服务`、`设备维保与健康监测`、`图书借阅大厅`
2. **场景聚焦与字数限制**：应用名称建议控制在 **2~8 个字** 之间，极其精准地突显核心业务实体与动作概念本身。

---

## 应用设计顺序

设计一个 HAP 应用时，应按以下顺序推进。每一步都依赖上一步的结论：

| 步骤 | 模块 | 核心问题 |
|------|------|----------|
| 1 | **角色权限** | 谁使用这个应用？各角色职责和权限边界是什么？ |
| 2 | **工作表** | 需要管理哪些业务对象？数据模型如何支撑各角色的工作？ |
| 3 | **业务规则** | 表单在填写时需要哪些动态显隐、自动设值和防错校验？ |
| 4 | **自动化工作流** | 哪些流程节点可以自动化？哪些需要人工触发？ |
| 5 | **自定义页面** | 管理者需要看到什么数据看板？一线操作者需要什么工作台入口？ |
| 6 | **导航分组** | 如何将上述所有内容组织成用户友好的入口层级？ |
| 7 | **外部门户** | 是否有外部用户需要受限访问？ |
| 8 | **AI 助手** | 是否有明确的智能查询或数据分析需求？ |

> **全局原则——以角色驱动设计**：角色是贯穿整个应用的设计主线。每个视图、自定义页面、工作流、自定义动作都应先明确“服务于哪个角色”，再决定内容。具体表现为：
> - **视图**：同一张工作表，不同角色看到不同的视图（数据范围、筛选条件、展示字段各异）
> - **自定义页面**：不同角色拥有各自的仪表盘或工作台（管理者看经营分析，操作者看待办任务）
> - **自定义动作**：按钮应只对有权操作的角色可见
> - **工作流通知**：通知对象应精确到角色，避免全员广播

## 一、角色权限（Role）

确定谁使用这个应用，以及他们能看到什么、操作什么。角色基于 RBAC 原则设计，用于定义数据范围、操作权限、审批责任和业务入口。

> **先想清楚「有哪些业务责任」，再决定「需要哪些数据权限」。**
> 角色不是组织架构，也不是岗位名单，而是一组可复用的业务权限能力。存量修订优先复用满足职责与权限边界的现有角色。HAP 支持一个用户拥有多个角色，因此应优先拆分清晰的业务角色，再通过多角色组合覆盖复合岗位。

---

### 系统预设角色

系统已包含以下预设角色，**不需要重复创建**：

| 预设角色  | 权限范围             |
| ----- | ---------------- |
| 管理员 | 所有权限（数据 + 应用配置）  |
| 运营者   | 所有数据权限 + 角色/用户管理 |
| 开发者   | 应用编辑权限（结构搭建）     |

设计时只需创建**业务角色**，无需创建「管理员」「超级管理员」「系统管理员」等系统级角色。

---

### 角色设计原则

#### 1. 按"业务职责"命名，而非"组织层级"

| 推荐         | 不推荐         | 原因            |
| ---------- | ----------- | ------------- |
| 借阅人员、图书管理员 | 普通员工、部门成员   | 层级描述，权限边界不清晰  |
| 采购专员、财务审核  | 采购部、财务部     | 部门不等于角色       |
| 销售代表、风控专员  | 业务人员、后台人员   | 职责过泛，无法指导权限设计 |
| 维修厂、供应商 、读者   | 外部用户、外部人员   | 应按外部协作职责命名    |
| ——         | 系统管理员、超级管理员 | 已由系统预设角色覆盖    |

#### 2. 按"权限差异"决定是否拆分

当角色在以下任一方面存在差异时，就应当拆分为不同角色：

* 能看到的数据范围不同
* 能操作的工作表不同
* 能执行的动作不同
* 参与的审批节点不同
* 使用的视图 / 自定义页面入口不同
* 内部角色与外部角色

#### 3. 利用"多角色组合"，避免创建过度复合角色

HAP 支持一个用户拥有多个角色。不要只按部门或业务域创建“大角色”，例如“销售”“采购”“财务”等；应根据该业务域下的权限差异，拆分为职责清晰的角色。

如果一个人同时承担多个职责，应为其分配多个角色，而不是创建一个覆盖全部权限的复合角色。

| 不推荐 | 推荐 |
|---|---|
| 销售 | 销售主管 + 客户经理 + 一线销售 |
| 采购 | 采购申请人 + 采购审批人 + 采购执行人 |
| 财务 | 财务审核人 + 出纳 + 费用管理员 |
| 门店 | 门店店长 + 库存管理员 + 收银员 |
| 项目 | 项目经理 + 任务负责人 + 项目成员 |

#### 4. 识别外部角色

当业务流程中可能需要**非本组织成员**参与协作时，应设计专门的外部角色。外部角色通过 HAP 外部门户访问应用，数据隔离需要通过真实的用户与业务记录关联、角色权限共同实现，不能仅凭门户入口推定已隔离。

识别信号：
- 合作方、供应商、客户、加盟商、外部读者等需要在系统中填报、查看或确认数据
- 业务流程中存在"跨组织边界"的协作环节（如维修厂接单、供应商报价、客户查看进度）
- 需要限制数据可见范围到"仅与自己相关的记录"
- 当同一角色既有内部协作关系，又有外部协作关系时（如维修厂既有内部管理人员，又有外部维修人员）应设计两个角色

外部角色原则上仅授予与本人或所属企业相关的记录，须明确关联依据并落实权限，不能假定平台自动配置。通常不参与内部审批流程，但可以作为流程的发起方或接收方；门户整体设计见「外部门户」章节。

---

### 权限层级参考

| 层级   | 数据范围                   | 适合角色              |
| ---- | ---------------------- | ----------------- |
| 只读   | 查看指定范围记录，不能修改          | 管理层、观察者、汇报对象      |
| 操作员  | 新增、编辑自己负责的记录           | 一线录入人员、业务经办人      |
| 协同处理 | 查看并处理与自己相关的记录          | 维修厂、供应商、客服等外部协作方  |
| 主管   | 查看和编辑团队或本机构范围内记录       | 团队负责人、设施管理者、部门负责人 |
| 审核人  | 查看待审核记录，并执行审批、驳回、确认等动作 | 财务审核、风控专员、法务审核    |

> 按成员字段鉴权：将工作表责任成员字段设 `config.userPermission: 2`（拥有者）或 `1`（只读），角色配 `recordDataScope: 20` 即自动生效；跨表按站点/项目负责人鉴权时，通过默认值（`relation`）或业务规则（`rcid`）将关联负责人同步至本表 `userPermission: 2` 成员字段。

---

### 完整性检查

生成业务角色后，按以下清单逐项检查是否遗漏：

| 角色类型   | 说明                    | 示例                 |
| ------ | --------------------- | ------------------ |
| 一线操作角色 | 负责日常录入、跟进、处理业务数据      | 销售代表、咨询员、仓管人员、维保专员 |
| 业务管理角色 | 负责团队监督、进度跟踪、异常处理      | 销售主管、设施管理者、车队管理员   |
| 审批审核角色 | 负责关键节点审批、复核、确认        | 财务审核、风控专员、采购审批人    |
| 专业支持角色 | 负责某类专业业务处理            | 法务专员、评估员、财务专员      |
| 外部协作角色 | 通过门户或受限入口参与业务（外部角色）   | 维修厂、供应商、客户、合作机构    |
| 只读分析角色 | 查看统计、报表、驾驶舱，不直接操作数据   | 管理层、法人管理者、观察者      |

不是每个应用都必须包含所有类型，但需要根据业务流程判断是否需要。注意"管理层"通常应优先作为只读分析角色，除非其确实参与审批或业务处理。

## 二、工作表（Worksheet）

数据是应用的基础。工作表设计决定了整个应用的信息结构。

### 两类工作表

| 类型 | 特征 | 典型例子 |
|------|------|----------|
| **基础资料类**（Master Data）| 主数据，相对稳定，被其他表引用 | 客户、图书、设备、员工、商品 |
| **业务过程类**（Transactional Data）| 流程记录，随业务持续产生 | 订单、申请、借阅记录、巡检记录 |

### 命名准则

- **基础资料类**：直接用业务对象名（名词单数）。✅ `图书`、`客户` &emsp; ❌ `图书列表`、`客户信息表`
- **业务过程类**：对象 + 动作名词。✅ `借阅记录`、`采购申请`、`维修工单`

### 建表判断

**建表前问自己**：这个对象需要独立的生命周期管理吗（需增删改查）？

- **是** → 独立建表，通过关联字段引用
- **否**（只是分类标签）→ 用单选 / 多选字段，不建表

### 核心原则

- **单一数据源**：同一业务对象只建一张表，用字段区分状态，用视图区分角色视角，用权限控制访问范围
- **状态机思维**：业务对象的不同阶段是同一张表里的状态字段。"待审批"和"已审批"是状态值，不是两张表

### 误用边界

- 不要按角色拆表——权限差异通过角色配置解决
- 不要把流程阶段拆成多张独立表
- 分类不需要单独管理时，用单选字段，不建表

## 三、字段（Field）

### 系统默认字段

每张工作表创建时自动包含以下系统字段，**不需要在设计中额外添加**：

- **创建时间**（ctime）
- **创建者**（caid）
- **最近修改时间**（utime）
- **最近修改人**（uaid）

> 如果业务需要的"创建时间""创建人"语义与上述系统字段一致，直接复用即可，不要重复建字段。

### 字段完整性

设计一张工作表字段时，按以下 8 个维度依次补齐。**每个维度至少覆盖 1 个字段**，不得遗漏任何维度：

| 维度 | 说明 | 典型字段示例 |
|---|---|---|
| ① 主标识 | 名称、编号、标题、组合标题——让用户一眼识别这条记录 | 书名、订单编号、工单标题、客户名称-联系人 |
| ② 核心业务属性 | 该业务对象的**核心描述信息**，体现行业特征 | ISBN、出版社、页数、作者（图书）；规格、品牌、产地（商品）；联系人、行业（客户） |
| ③ 状态与分类 | 状态流转、类型分类、优先级 | 借阅状态、图书分类、紧急程度、审批状态 |
| ④ 时间维度 | 业务相关的时间节点（系统默认字段已含创建时间/修改时间，无需重复） | 借出日期、应还日期、截止日期、完成时间、有效期 |
| ⑤ 责任与协作 | 负责人、审批人、操作人（系统默认字段已含创建者/修改人，无需重复） | 经办人、管理员、借阅人、审批人 |
| ⑥ 数量与金额 | 数量、金额、统计值——支撑工作流的加减运算 | 库存数量、单价、总金额、累计次数 |
| ⑦ 说明与凭证 | 备注、附件、图片、富文本说明、签名 | 图书封面、备注（`Text` 多行）、合同附件、图书简介（`RichText`）、电子签名（`Signature`） |
| ⑧ 计算与衍生 | 由其他字段自动计算/引用/汇总得到的值，用户无需手动填写 | 应付金额=数量×单价（Formula）、逾期天数（DateFormula）、客户名称（Lookup）、历史订单总额（Rollup）、显示编号（文本组合/Concatenate） |

> ⚠️ **维度 ② 是最容易被忽略的维度**。很多设计只有名称+状态+时间，缺少真正体现业务对象特征的属性字段。例如「图书」表只有书名和作者，缺少 ISBN、出版社、出版日期、页数、语言、馆藏位置等关键业务属性。

### 业务场景字段补全（主动识别并在设计中给出）

根据工作表所属的业务场景，主动补齐以下常见但容易遗漏的字段：

**主数据 / 资料类**（客户、图书、设备、商品、员工）：
- 图片/封面（Attachment）、简介/描述（RichText）
- 所在位置/地址（Location 或 Text）
- 启用状态（SingleSelect 或 Checkbox）
- 行业特征属性（如图书的 ISBN/出版社/页数；商品的规格/品牌/产地；设备的型号/序列号/购入日期）

**单据 / 记录类**（订单、借阅记录、工单、入库单）：
- 单据编号（AutoNumber）、操作人（Collaborator）、操作时间（DateTime）
- 处理状态（SingleSelect，**必须包含完整状态链**，覆盖从创建到结束的所有状态）
- 来源/渠道（SingleSelect）

**涉及库存 / 数量的表**：
- 总量、已用量/在借量、可用量/剩余量（Number）
- 确保能支撑工作流中的加减运算（如借出时 `可借库存 -1`，归还时 `可借库存 +1`）

**涉及审批 / 流转的表**：
- 审批状态（SingleSelect）、审批人（Collaborator）、审批时间（DateTime）、审批意见（Text）
- 需要签字确认的场景（如验收单、交接单）→ 加 `Signature` 电子签名字段

**涉及计算 / 衍生字段的表**：
- **【强约束】主子表必配 `Rollup`（汇总）**：凡是在主表中声明了 `SubTable`（如 采购明细、费用明细、合同明细、订单明细），主表**必须至少配 1~2 个 `Rollup` 字段**计算总金额或总数量（如明细总金额、商品总件数、明细条目数），主表无汇总等于残缺设计。
- **【按用途选择】Lookup 展示与存储**：表单需要独立展示关联值时使用仅显示 Lookup（`storeData: false`），关联卡片已满足展示时可复用卡片；本表文本组合（`Concatenate`）、公式或分组/统计筛选需要引用该值且不构成跨表衍生循环依赖时，使用存储型 Lookup（`storeData: true`），并核对同步要求。不因工作流取值需求开启 Lookup 存储或改变字段类型；来源取值由工作流领域处理。来源已明确时，本表关联字段与 Lookup 可同批创建，无需普通字段占位。
- **【强烈推荐】业务单据/流转记录 标题必配 `Concatenate`（文本拼接组合）**：对于没有天然单一短名称的业务单据/流转记录（如 借阅记录、出入库单、调拨单、维修工单、会议预约、审批申请、巡检记录），其标题字段（isTitle）**强烈推荐使用 `Concatenate` 组合字段**，自动拼接核心维度生成格式化标题（如借阅摘要拼接图书与借阅人、调拨单全称拼接调出仓与调入仓及日期、工单全称拼接设备与故障类型）。
- **日期差值/偏移**：需要计算两个日期差值（如"逾期天数=当前-应还日期"）→ `DateFormula`（formulaType=dateNowDiff）；需要日期偏移（如"到期提醒日=到期日-3天"）→ `DateFormula`（formulaType=dateOffset）。
- **条码生成**：需要生成条码/二维码（如资产标签、工号牌）→ `Barcode`。

**涉及前端交互扩展 / 复杂渲染的表**：
- **【克制推荐】原生无法满足的可视化与特殊交互 → `CustomField`（自定义字段）**：
  - **适用场景**：仅在明道云原生字段（文本/数值/单选/评分等）无法满足业务表现力时使用。典型包括：履约进度条/步骤指示环、九宫格数字输入器、复杂状态视觉卡片、多字段聚合汇总卡片；
  - **模式选型**：
    - 需要存值与回写数据库（参与筛选/统计/工作流）→ 选 **存储型**（提供 value / onChange 回写）；
    - 仅读取当前记录其他字段做展示计算（不占数据库存储空间）→ 选 **引用展示型**（消费 formData 只读渲染）；
  - **克制红线**：普通单选/多选、常规 1~10 评分（用 `Rating`）、普通布尔判断（用 `Checkbox`）以及纯数值计算（用 `Formula`）严禁使用自定义字段替代。

**涉及层级 / 树形分类的表**（如区域、品类、组织架构）：
- 分类表自身有父子关系 → 本表 `Relation`（dataSource=selfRelation）
- 其他表需要按分类层级选择 → `CascadingSelect`（级联选择，关联分类表的层级视图）

**涉及明细 / 子项的表**（如订单明细、报价项目、费用条目）：
- 明细数据从属于主记录、不独立管理 → `SubTable`（子表）
- 明细需要独立管理/被多表引用 → `Relation`（关联独立表）


### 选型规则

* 单行 / 多行纯文本 / Markdown → `Text`（`textMode: singleLine | multiLine | markdown`，无 `Textarea`）
* 带格式长文本 → `RichText`
* 普通数值 → `Number`
* 金额 → `Currency`
* 固定单值枚举 → `SingleSelect`
* 固定多值枚举 → `MultipleSelect`
* 选项较多需搜索 → `Dropdown`
* 只要日期、年、年月 → `Date`
* 要具体时点 → `DateTime`
* 只要时间（不含日期） → `Time`
* 单个是/否 → `Checkbox`（不要用 SingleSelect + 是/否）
* 1～10 级评分 → `Rating`
* 手机号 → `PhoneNumber`
* 座机/电话 → `LandlinePhone`
* 邮箱 → `Email`
* 定位坐标 → `Location`
* 省市区行政区域 → `Region`
* 负责人/审批人 → `Collaborator`
* 部门归属 → `Department`
* 组织角色 → `Role`
* 跨表引用/联动/关联记录 → `Relation`
* 本表父子层级（上级任务/父分类）→ `Relation`（dataSource=selfRelation）
* 子表/明细数据 → `SubTable`
* 引用他表字段（只读/带入）→ `Lookup`
* 汇总他表数据（求和/计数/均值等）→ `Rollup`
* 简单数值四则运算 → `Formula`；需要函数表达式的计算 → `FunctionFormula`，不替换已满足需求的专用计算类型
* 日期计算/差值/偏移 → `DateFormula`
* 文本拼接组合 → `Concatenate`
* 单据流水号 → `AutoNumber`
* 材料/图片/文件 → `Attachment`
* 电子签名 → `Signature`
* 条码/二维码 → `Barcode`
* 前端自定义渲染/交互脚本组件 → `CustomField`（自定义字段）

### 关联字段规则

仅在以下情况建立 `Relation`：

* 需要引用另一张表记录
* 需要与另一张表联动
* 需要基于另一张表筛选、统计、回写
* 需要表达本表父子层级

### SubTable vs Relation 选型

当主表需要关联多条明细记录时，需判断用 `SubTable`（子表）还是 `Relation`（关联表）：

| 判断维度 | 用 SubTable | 用 Relation |
|---|---|---|
| 数据归属 | 明细记录**从属于主记录**，不独立存在 | 被引用实体是**全局共享**的 |
| 生命周期 | 子记录随主记录创建/删除 | 被引用记录独立管理 |
| 复用性 | 不会被其他表引用 | 可被多张表引用 |
| 管理方式 | 仅从主表记录入口编辑，在应用导航栏设为隐藏（displayType: 2） | 需要独立视图、筛选、导出 |

**用 SubTable 的典型场景**：采购明细行、报价项目、行程安排、费用明细、合同条款、评分项、考核指标

**用 Relation 的典型场景**：客户、商品、员工、部门、仓库、供应商

### 单向关联 vs 双向关联选型

在建立 `Relation` 跨表关联时，必须根据业务关系的主从属性与穿透需求确定方向：

| 关联方向与角色 | 行为表现 | 适用典型场景 |
|---|---|---|
| **单向引用** | 仅源表显示关联下拉选择，目标表**不生成反向字段** | **基础主数据与字典引用**：<br>- 单据选仓库/供应商/经办人（如 出库单 选 仓库）<br>- 明细反查主数据（如 采购明细 选 商品、工单 选 设备）<br>- 辅助分类与字典引用（如 报销选费用科目、工单选故障类别、任务选部门） |
| **双向主创建端** | 源表有关联选择，目标表**自动生成反向 Tab 标签页表格** | **核心业务主从穿透管理（主动发起端）**：<br>- 单据端关联主表（如 请假单关联审批、订单关联客户）<br>- 多对多发起端（如 项目关联员工）<br>- 平级业务协同（如 订单 ↔ 发票） |
| **双向反向承接端** | 目标表通过对端生成的反向关联展示名下数据 | **主表/聚合表查看名下业务流水（被动承接端）**：<br>- 审批表看请假记录、客户表看历史订单、员工表看参与项目 |

> 💡 **设计准则**：
> - **保护主数据表整洁**：对「商品、仓库、分类、字典、物料」等被广泛引用的基础表，务必使用 **单向引用**，避免基础表表单被数十个不同单据的反向明细列表严重污染。
> - **双边声明规范**：双向关联中，同时明确单据端/发起端和主表端/承接端的业务关系；Build 的紧凑语法与创建规则由 `hap-app-plan-builder-spec` 维护。
> - **按需穿透才建双向**：只有当用户在目标表详情页**确实需要自顶向下穿透查看/管理关联记录**时，才配置为 **双向关联**。

### 误用边界

* 状态、类型、优先级不要用 `Text`
* 负责人不要用姓名文本，优先用 `Collaborator`
* 不要把所有字段都做成 `Text`
* 不要仅因"查看方便"建立关联
* 不要过度设置必填字段
* 不要只生成总览里提到的几个字段就停止

## 四、业务规则（Business Rule）

业务规则可在前端/后端直接控制字段显隐、只读、必填、动态赋值与数据锁定。

### 规则类型速查

| 类型 | 关键词 | 适用场景 |
|---|---|---|
| **交互规则** | 显隐、只读、必填、设值 | 根据条件动态控制字段属性，或自动设置字段值（可替代简单的反写工作流）。**字段显隐统一使用 show 动作**（满足条件时显示，不满足时自动隐藏） |
| **验证规则** | 校验、拦截、阻止提交 | 提交前校验数据合规性，支持开启**后端校验**拦截 API 和 Excel 导入的脏数据 |
| **锁定规则** | 冻结、禁止编辑、删除 | 终态记录（已打款、已作废、已归档）整条锁定，每表仅限一条 |
| **样式规则** | 颜色、加粗、字号 | 按条件高亮字段标题或值的视觉样式 |

### 主动识别信号（何时必须输出业务规则）

> 当工作表命中以下任一信号时，**必须主动为其设计业务规则**。不输出等于放任表单裸奔。Build 的业务规则产物字段由 `hap-app-plan-builder-spec` 维护。

| 识别信号 | 应配置的规则 | 典型描述示例 |
|---|---|---|
| 存在**状态流转字段**，不同状态下用户应看到不同的字段 | 交互：show | 当状态流转到审批通过后，才显示审批相关字段，如：审核时间、打款时间等 |
| 存在**审批流转**，进入审批后申请人不应再修改数据 | 交互：只读全部字段 | 当状态不是草稿且不是已退回时，所有业务字段设为只读 |
| 存在**子表/明细**，且主表有状态流转 | 交互：子表权限 | 当状态进入审批后，子表禁止新增和删除明细 |
| 存在**终态**（已打款/已作废/已归档/已完成） | 锁定 | 当状态为已打款或已作废时，锁定整条记录 |
| 存在**金额/数量**等关键数值，需防止零值或负值 | 验证（后端校验） | 后端校验：报销总金额必须大于 0 |
| 存在**日期先后约束**（开始 vs 结束） | 验证（后端校验） | 后端校验：结束日期不得早于开始日期 |
| 存在**条件必填**（某分类下才需要填写的字段） | 交互：show + 必填 | 当报销类型为差旅报销时，显示并必填出差目的地 |

> **柔性描述原则**：描述涉及多个字段时，采用"业务意图 + 举例"的方式（如"当审批通过后，才显示审批相关字段，如：审核时间等"），避免死板穷举字段名。搭建阶段会基于实际创建的完整字段列表（含建表时补充的字段和分段）智能匹配所有符合意图的字段。

### 误用边界

- **计算与触发方式分开选择**：持续衍生值使用公式，初始值使用字段默认值，条件显隐/必填/校验使用业务规则。字段前端事件属于字段配置，不等同于业务规则；仅用户明确要求前端事件或特定前端触发行为时使用，不因“优化表单”自动增加。具体选型与修改规则统一见 `hap-domain-worksheet-spec`，参数以实时 MCP Schema 为准。
- **跨表操作按时机选型**：业务规则不承担跨表查询或外部调用；填写时取默认值或用户明确要求的前端动作按字段接口实际能力配置，保存后、定时或无人打开表单的处理使用工作流。前端事件不代替服务端校验与权限，不因需要跨表取值就一律改用工作流。
- **注意规则冲突**：规则自上而下顺序执行，避免多条规则在重叠条件下对同一字段产生矛盾指令

## 五、视图（View）

### 默认设计规则

每张工作表至少应有 1 个Table 类型的 `全部` 视图：用于完整浏览、筛选、排序、分组、批量处理

根据工作表的业务场景、字段结构与角色查看需要，增加 2～4 个其他视图（含默认视图共 3～5 个）。

### 视图排序

先判断每个视图的使用频率和业务作用，再按以下优先级排列：

1. **主工作入口视图** — 用户打开工作表后最先使用的视图
2. **待处理 / 高频操作视图** — 如 `我的待办`、`待审批`
3. **核心业务推进视图** — 如状态看板、项目甘特图
4. **重要浏览辅助视图** — 如画廊、日历、地图
5. **管理分析视图** — 如按部门分组、按月统计
6. **`全部` 视图** — 兜底管理视图
7. **归档 / 取消 / 日志视图** — 低频查阅

不要按视图类型固定排序；Gallery、Kanban、Calendar、Gantt、Map 如果承担主工作入口，应直接排第一。例如：
- 图书表的 `可借图书`（Gallery）、任务表的 `任务看板`（Kanban）、排班表的 `本周排班`（Calendar）
- 项目表的 `项目排期`（Gantt）、网点表的 `网点地图`（Map）

> `全部` 是兜底管理视图，不要求排第一；但对于**配置表、字典表、日志表、基础资料表**等低频表，`全部` 可以排第一，且可只保留少量必要视图。

### 字段、业务驱动的视图

当工作表的业务和字段结构与某类视图高度契合时，**必须**主动添加该类型视图

| 字段条件 | 必须添加的视图 | 说明 |
|---|---|---|
| 存在 selfRelation 或指向本表的 Relation | `Hierarchy` | 天然的父子树结构，用 Table 无法直观展示层级 |
| 存在状态/阶段类 SingleSelect（选项 ≥ 3） | `Kanban` | 状态流转是看板的核心场景 |
| 存在 Location 定位字段 | `Map` | 地理分布只有地图视图能直观呈现 |
| 附件字段是表的核心内容（如产品图、案例封面） | `Gallery` | 图片化浏览是 Gallery 的不可替代优势 |
| 表的业务语义是任务/排期，且有计划开始+结束日期 | `Gantt` | 项目排期、任务计划等需要时间轴视角 |
| 表的业务语义是排班/预约，且有时间段+人员/资源字段 | `Resource` | 资源占用与时间冲突只有资源视图能直观呈现 |
| 表是参数配置/系统设置，通常只有 1 条记录 | `Detail`（mode=first） | 单记录场景无需列表，直接展示详情 |

### 按角色设计视图

不同角色对同一张工作表的关注点不同，应通过视图区分角色视角，而非按角色拆表：

* 一线操作者 → 「我的待处理」「我负责的」等筛选型视图，只看自己相关的数据
* 业务管理者 → 「全部记录」「团队待办」等全局视图，用于监控和分配
* 审批角色 → 「待我审批」视图，按审批状态筛选
* 只读分析角色 → 按需分配已有视图的查看权限即可，通常不需要专属视图

视图与已保存筛选器用于组织业务入口和常用查询条件；筛选不替代角色权限，数据隔离由实际访问权限保证。临时查询不必新建视图。

### 选型规则

* 批量浏览、筛选、编辑、导出 → `Table`
* 当前人查看自己相关数据 → 增加筛选型 `Table` 视图，如 `我的待处理`；仅允许访问自己数据仍须配置权限
* 状态泳道、拖拽推进 → `Kanban`
* 看某天有什么 → `Calendar`
* 看任务起止与排期 → `Gantt`
* 看图片内容（产品、案例、简历）→ `Gallery`
* 看单条完整信息 → `Detail`
* 看父子结构 → `Hierarchy`
* 看地理分布 → `Map`
* 看资源/人员占用与排班 → `Resource`

### 误用边界

* 有日期字段，不代表一定建 `Calendar`
* 有开始/结束日期，不代表一定建 `Gantt`
* 有附件字段，不代表一定建 `Gallery`
* 有关联字段，不代表一定建 `Hierarchy`
* 不要因为"要分组"就一律用 `Kanban`，很多场景更适合 `Table + 分组`
* 每张工作表视图建议不超过 5 个

## 六、自定义动作（Custom Action）

工作表记录上可以配备操作按钮（自定义动作），这是串联业务流程的核心人工入口。

### 三种类型

1. **填写当前记录**（`update`）：将一组字段归类填写，方便用户集中操作。
   > 适用：需要用户**主动输入内容**才能推进流程的场景
   > 例：点击「更新图书信息」按钮，弹出表单让用户填写
   > 💡 **支持提交后触发工作流**（`runWorkflowAfterSubmit: true`）：适用于填完表单后需进一步自动流转的场景（如填写跟进记录后自动修改线索状态并通知负责人）。

2. **新建关联记录**（`create`）：用户点击按钮新建一条关联记录
   > 适用：用户在当前记录上**发起一件需要填写信息的新事务**
   > 例：在「设备」记录上点击「报修」按钮，填写「报修申请」
   > 💡 **同样支持提交后触发工作流**（`runWorkflowAfterSubmit: true`）：适用于创建完关联记录后需要自动化联动的场景（如创建报修申请后自动将设备状态置为“维修中”并派单）。

3. **直接触发工作流**（`trigger`）：不弹出表单，点击后直接触发工作流自动处理
   > 适用：业务推进**不需要用户输入**，系统自动完成
   > 例：借阅记录上的「归还」按钮——状态自动改为已归还、归还日期自动写入今天、库存自动加一

### 挂载规则

动作必须挂在**动作发起的数据源头表**上，不要挂在目标表上。

* 发起借阅 → 挂在图书表，不挂借阅记录表
* 发起工单 → 挂在客户表，不挂工单表
* 登记归还 → 挂在借阅记录表，不挂图书表

### 操作入口与数据源

* 按业务需要配置记录详情、行内或卡片快捷操作、视图多选后的批量操作；批量入口目前支持普通表格和树形表格，不默认挂载全部入口。
* 直接触发工作流的动作可选单数据源或多数据源，与入口独立：单数据源在多选时逐条触发；多数据源将选中记录作为集合交给一个主流程，也可处理详情或快捷入口传入的一条记录。
* 各记录独立办理选单数据源；合单、集合统一更新或删除、汇总报送选多数据源，不能仅凭“批量操作”决定数据源类型。
* 数据源类型在创建时确定，切换需要重建动作，具体执行遵循动作领域规范。

> 💡 **工作流联动与操作便利性原则**：
> * 自定义动作不只有「直接触发工作流（`trigger`）」能跑工作流，「填写当前记录」和「新建关联记录」在提交表单后**同样可以设置为触发工作流**（配置 `runWorkflowAfterSubmit: true`），用于处理“人工收集必要信息 + 系统自动完成后续流转”的复合场景；人工输入须有实际字段承接。
> * 即使单纯做数据维护、不触发工作流，也应为高频操作（集中填写特定字段、快速新建关联单据）提供自定义动作，大幅提升用户的操作便利性。

### 误用边界

* 严禁在没有直接物理关联（Relation）字段的两张表之间，设计并生成“新建关联记录”类型的自定义动作。规划此类动作时，**必须同时提供源工作表中用于物理关联的具体 Relation 字段名称**。如果两张表之间在规划中没有直接的 Relation 字段，则禁止规划此类动作，而应当：
  - (1) 在源工作表中配套 Relation 关联字段，并在动作中引用它；
  - (2) 或者将自定义动作的类型设计为“直接触发工作流(trigger)”，利用后台工作流自动创建对应记录。
* 不要把"新建关联记录"类动作挂在目标表上
* 不要让需要人工输入的场景用 `trigger`
* 不要把本可自动完成的动作做成 `update/create`
* 如果字段值是"今天""当前用户""固定状态"等系统可自动确定值，通常不应要求用户手填
* 不需要人工点击的场景 → 改用自动化工作流，不做自定义动作
* **严禁创建「审批通过」「审批驳回」「审批否决」等直接操作审批结果的按钮**。审批流程的正确设计：用户点击「提交审批」或「发起审批」按钮（`triggerWorkflow` 类型动作），或新建记录时自动触发（`worksheet_event`），由工作流内部的审批业务块 (`approval_block`) 流转——通过/驳回由审批人在审批节点中操作，不是自定义动作按钮

## 七、自动化工作流（Workflow）

工作流是业务流程的自动化执行，减少重复人工干预。

> **核心原则**：先理清业务流程，再考虑自动化。自动化只是加速，不能替代对流程本身的设计。

### 触发方式选型

| 触发方式 | 适用场景 | 典型应用 |
|----------|----------|----------|
| 工作表事件（`RecordEvent`） | 记录新增 / 编辑 / 删除后立即触发 | 通知推送、状态同步、数据联动 |
| 日期字段（`DateField`） | 基于记录中某日期字段相对触发 | 到期提醒、定期跟进、续费预警 |
| 定时（`Scheduled`） | 固定周期执行 | 逾期检查、周期汇总、盘点提醒 |
| 自定义动作（`CustomAction`） | 用户主动点击按钮后触发 | 审批提交、确认归还、发起退款 |

### 触发合理性与前置条件

* **工作表事件（`RecordEvent`）**：
  * **事件类型与触发条件**：明确为「新增」、「编辑」、「新增和编辑」或「删除」，所有事件类型均可设置触发条件（如新增且类型为VIP）。
  * **监听修改字段**：涉及编辑（含新增和编辑）时，通常应明确指定监听的修改字段（如订单状态）；下游回写本表时还需核对是否会再次满足触发条件；监听字段与回写字段重叠时应有明确的状态迁移、幂等条件或退出条件，指定监听字段本身不能保证避免循环。
* **日期字段触发（`DateField`）**：
  * 明确基准日期字段与相对时间偏移（如截止日期前 30 分钟）。
  * 提醒/催办等场景通常应设置状态过滤（如排除已完成、已取消的记录），避免对已完结数据产生误扰。

### 动作能力与场景选型

以下是整体业务规划可用的能力概览。主 Agent 据此确定目标、业务约束和必要依赖，交给工作流设计/执行器选择和组合节点；不在业务意图中预写节点顺序、别名、物理 ID 或请求 JSON。详细节点选型和作用域说明由 hap-workflow-design-guide 承载，无需为规划常规业务加载全部执行参数。

* 生成新单据/流水 → 新增记录 (`add_record`)
* 推进状态/自动赋值/联动回写 → 更新记录 (`update_record`)
  * 条码/二维码是由生成配置自动派生的展示字段，不能直接赋值。需要改变编码内容时，应更新其实际引用的可写来源字段
* 删除特定记录 → 删除记录 (`delete_record`)（⚠️ 仅在必要时使用，优先使用更新状态为已作废代替）
* 按条件定位一条后立即更新/删除 → 查找并更新 (`find_and_update`) / 查找并删除 (`find_and_delete`)
* 对已有选中记录集合统一赋值/清空或删除 → 直接更新 (`update_record`) / 删除 (`delete_record`)；需要按工作表条件查找一批记录时，使用批量更新 (`find_and_batch_update`) / 批量删除 (`find_and_batch_delete`)。逐条处理的选型遵循工作流设计指南；删除同样优先考虑作废状态。
* 从已有记录的关联字段中取数 → `get_related_record`（一条）/ `get_multiple_from_field`（集合），可进一步筛选；后续操作引用获取到的记录
* 在目标工作表中按条件查询 → `get_single`（一条）/ `get_multiple`（集合）；包括查询“目标表的关联字段关联了来源记录”，具体选型见 hap-workflow-design-guide
* 从已查到的多条结果中按规则或随机取一条 → `get_single_from_multiple`
* 对查询结果统计 → 汇总 (`rollup`)
* 动态计算数值或日期 → 计算 (`compute`)（包含数值公式、日期差值 `dateDiff`、日期偏移 `dateOffset`）
* 触达相关人员 → 站内通知 (`send_internal_notice`) / 抄送 (`cc`) / 邮件 (`send_email`) / 短信 (`send_sms`)。短信、邮件均支持人员、部门、组织角色、职位、应用角色和触发人，也支持各自的固定联系方式及手机/邮箱/文本字段；具体来源须由执行器按当前 MCP 契约落实。短信可直接拟定正文，变量取字段值，需组织可用签名；港澳台/国际发送需组织集成相应短信服务。手机、邮箱不能当作站内通知或抄送的人员身份。
* 流程等待或延迟 → 延时 (`delay`)（支持等待固定时长或延迟到指定时间）
* 条件不满足时提前结束流程 → 中止流程 (`terminate_process`)
* 引入人工决策与流转 → 审批业务块 (`approval_block`)（从发起审批开始，内部可包含审批 `approve`、填写 `fill_in`、抄送节点）
* 将一组处理封装为内部流程 → 子流程 (`sub_process`)（支持单次处理、并行逐条或串行逐条；规划时明确是否依赖处理顺序、是否全部完成后才能继续，具体方式由下游设计）
* 按次数或直到条件满足重复执行 → 循环 (`loop`)（如重试、分期生成；须有退出条件与最大次数，逐条处理记录用子流程）
* 按条件分流 → 条件分支 (`branch`)
* 与外部系统交换数据 → HTTP 请求节点 (`webhook`)（如推送订单、查询物流；明确接口用途、请求数据和返回结果如何影响本应用）
* 使用接口返回的 JSON 数据 → JSON 解析 (`json`)（明确数据来源、需要使用的结果及解析失败后的业务处理）
* 现有节点无法表达的数据处理 → 代码块 (`code`)（支持 JS / Python；已有 HTTP 请求、JSON 解析或计算能力能满足时优先使用对应节点）


### 外部对接的规划前提

* 交接业务目标时说明外部系统、接口用途、输入数据、返回结果的业务含义、需要回写的字段，以及失败或重复提交时的处理要求。比如“将已审核订单同步到物流系统，保存物流单号；失败时保留待处理状态并通知经办人，避免重复建单”。
* 已知的接口文档或配置来源随任务交接；地址、认证方式、响应结构等必要信息缺失时明确列出依赖，不编造接口、凭证或响应字段。主 Agent 不必先完成请求参数设计。
* `webhook` **动作节点**是向外发送 HTTP 请求，Webhook **触发器**是接收外部请求后启动流程，两者独立。节点可用不代表当前搭建入口已接入该触发方式；具体触发支持范围遵循调用方的产物协议和执行能力，不能自行增加触发类型。

### 误用边界

* 不要用 `Scheduled` 做实时通知（应使用工作表事件触发）
* 不要把高频变化规则写死在节点里，优先用字段值 + 条件分支
* 不要给所有流程都套审批
* 目标涉及数据或状态变化时，通知不能替代必要写入；纯提醒流程可以只通知，不为凑闭环新增无关写入
* 删除记录要谨慎，很多场景更适合"更新状态为已作废"
* 含有不确定人工判断的步骤不要自动化，用自定义动作让人来决策

## 八、统计图表（Chart）

工作表统计图用于表内分析，自定义页面图表用于页面中的看板与工作台，两者可使用相同工作表数据源，但属于不同配置对象。修改时沿用图表所属入口，保留未要求改变的统计口径、时间范围与布局；具体操作由对应领域规范维护。

### 默认设计规则

一个 dashboard 优先覆盖以下 3 类问题：

1. 核心指标总览
2. 时间趋势变化
3. 结构占比或排行对比

只有业务明确需要时，再补充漏斗、透视、雷达、散点、瀑布、玫瑰、矩形树图、桑基等图表，不为丰富类型而凑图。

### 选型规则

本节用于业务方案选型，中文名称帮助理解，括号内标识与 MCP `chartType` 一致，用于方案输出并保持大小写。执行器依据 `hap-chart-design-guide` 与实时 MCP Schema 配置，本节不定义接口参数。

按以下顺序选型：先确定要回答的业务问题，再检查可用或已规划的数据是否具备所需字段与统计口径，最后在适用类型中选择最容易读懂的一种。精确比较分类大小优先柱形图或条形图，不能仅为视觉丰富选择复杂图表。用户明确指定类型时先检查适用条件；不满足时说明缺口与可行替代，不擅自换图或改变统计定义。

* 看关键数字 → 数值图（`numberChart`）
* 看完成率 / 达成度 → 仪表盘（`gaugeChart`） / 子弹进度图（`progressChart`）
* 看类别对比 → 柱形图（`columnChart`） / 条形图（`barChart`）
* 看名称较长的类别对比 → 条形图（`barChart`）
* 看时间趋势 → 折线图（`lineChart`）
* 看双指标趋势 → 双轴图（`dualAxisChart`）
* 看占比构成 → 饼图（`pieChart`）
* 看分类数值的放射状对比 → 玫瑰图（`roseChart`），精确比较大小优先柱形/条形图
* 看分类数值的面积构成 → 矩形树图（`treemapChart`）
* 看各项增减贡献与累计结果 → 瀑布图（`waterfallChart`）
* 看多层分类之间的流向与权重 → 桑基图（`sankeyChart`）
* 看阶段转化 → 漏斗图（`funnelChart`）
* 看排行榜 / TopN → 排行榜（`rankingChart`）
* 看双侧群体对比 → 对称条形图（`symmetricBarChart`）
* 看多指标综合比较 → 雷达图（`radarChart`）
* 看两个数值变量关系 → 散点图（`scatterChart`）
* 看多维交叉分析 → 透视表（`pivotTable`）
* 看中国行政区划分布（需地区字段） → 中国行政区划地图（`regionMap`）
* 看世界范围定位分布（需定位字段） → 世界定位地图（`worldMap`）
* 看文本热点 / 关键词分布 → 词云图（`wordCloud`）

### 图表设计规则

每个图表都必须先明确：

* 回答什么业务问题
* 指标是什么
* 按什么维度看
* 为什么适合当前统计入口；放入 dashboard 时，为什么值得进入首页

### 误用边界

* 不要多个图表回答同一个问题
* 不要堆过多 `numberChart` 或 `pieChart`
* `pieChart` 类别过多时改用 `barChart`
* 没有明确阶段顺序不要用 `funnelChart`
* `waterfallChart` 必须有可累计的增减口径，不能把各期余额当作增减额
* `sankeyChart` 必须有真实层级对应关系和统一权重口径，不能从当前状态推导历史流转路径
* `treemapChart` 用于分类构成，不因名称含“树”就承诺多级钻取；`roseChart` 的半径差异不能直接解释为占比
* 没有连续时间维度不要用 `lineChart`
* 没有 `Region` 字段不要用 `regionMap`，没有 `Location` 字段不要用 `worldMap`
* 每个 dashboard 建议 6~10 个图表

## 九、自定义页面（CustomPage）

> **页面分类**：自定义页面主要承担两种核心角色：
> 1. `dashboard`：以数据统计、趋势分析为主，聚合工作表数据、展示统计图表、支撑管理决策。
> 2. `workspace`：以快捷操作、任务处理为主，作为应用的门户入口、待办中心或核心业务流的操作台。

### 设计准则

**先明确页面目的**：每个自定义页面应回答一个具体的问题——服务于谁？帮助做什么？

| 页面类型 | 服务对象 | 内容侧重 |
|----------|----------|----------|
| dashboard | 需要看数据做判断的角色（管理者、分析者、一线操作者均可） | 趋势对比、多维交叉分析、聚合统计 |
| workspace | 需要高频操作的角色（一线操作者、全员） | 当前状态、待办处理、高频操作入口 |

**按角色规划页面**：不同角色的关注点和操作方式不同，应为其设计专属或共享的自定义页面：

* 管理者/决策者 → 经营分析仪表盘（核心），辅以管理工作台提供审批、督办等操作入口
* 一线操作者 → 操作工作台（核心），辅以业务仪表盘查看个人绩效、待办统计等数据
* 外部角色（供应商、客户、维修厂等） → 专属工作台（核心且推荐）。外部角色通过外部门户访问，工作台是其最优入口形式——聚合待办任务、进度查看、高频操作（如接单、报价、确认），提供集中的操作入口，数据访问仍由角色权限控制。必要时可辅以简要的业务仪表盘展示与自身相关的统计数据
* 按角色拆分 → 当不同角色关注的指标或操作有差异时，应分别创建独立的仪表盘或工作台，而非将所有内容合并到一个页面。只有当多个角色的关注内容完全一致时，才共享同一页面

### 页面组件生态 (Component Ecosystem)

自定义页面支持多种组件组合，以满足不同类型页面的需求：

1. **图表类 (Chart)**：如 `numberChart` (数值)、`barChart` (条形图)、`pieChart` (饼图)、`lineChart` (折线图) 等。主要用于聚合展示和分析（`dashboard` 核心）。
2. **筛选器组 (FiltersGroup)**：仪表盘的全局数据筛选器，一个组件内可包含多个筛选器（时间、状态、分类等）。用户通过筛选器切换维度，联动页面中的图表和视图。筛选器规划见下节。
3. **操作与数据类**：
   - **快捷按钮 (Button)**：快捷入口，配置创建记录/打开视图/打开页面/打开链接。
   - **内嵌视图 (View)**：将工作表的特定视图（如"待我审批的报销"、"进行中的项目"）直接嵌入页面。
   - 主要用于构建工作台和任务中心（`workspace` 核心）。
4. **展示与布局类**：
   - **富文本 / 网页内嵌 (Text / HTML)**：用于展示操作规范说明、规章制度或外部系统链接。
   - **轮播图 (Carousel)**：以图片轮播形式展示内容，视觉冲击力强，适合**展示型、浏览型**场景：
     - 推荐或精选内容展示
     - 公告/通知/活动轮播
     - 品牌宣传、活动海报
     - 重点项目/成果展示
   - **标题区 (Section)**：用于页面的视觉分区。

> 💡 **View vs Carousel 选型**：用户需要筛选/操作数据 → View；只需浏览了解（推荐、公告、展示） → Carousel。

### Dashboard 筛选器规划

Dashboard 页面必须包含 1 个 `FiltersGroup` 筛选器组，为用户提供按时间、状态、分类等维度切片分析的能力。规划时应从页面图表引用的事实表中，挑选最有分析切片价值的业务维度字段（如时间、状态、分类、部门等）。如果需要按时间筛选，必须显式声明（如`创建时间`或`ctime`）。

### 误用边界

- 不要混淆组件类型定位（如在 workspace 堆砌大量折线图，或在 dashboard 放置过多操作按钮）
- 不同页面应有明确的分工，不重复展示相同数据或入口

## 十、导航分组（Navigation Group）

导航结构决定用户进入应用后的第一印象和操作路径。

> **核心原则**：以用户的业务任务和使用场景为主线组织导航分组，兼顾核心业务对象，确保入口清晰、层级稳定、路径自然。

### 推荐结构（从上到下）

| 分组位置 | 推荐内容 | 说明 |
|----------|----------|------|
| 1. 总览 / 首页 | 自定义页面（Dashboard / Workspace）、AI 助手 | 让用户一眼掌握全局状态和核心待办 |
| 2. 核心业务 | 高频操作工作表 | 借阅管理、订单处理、工单跟进 |
| 3. 基础资料 | 主数据工作表 | 低频使用，放靠后 |
| 4. 配置与管理 | 分类维护表、基础数据表 | 极低频，由管理员维护 |

### 分组命名准则

- 优先使用简洁的业务场景词命名；如：借阅 优于 借阅管理，设备 优于 设备运维
- 组名 2～4 字，应简洁、明确
- 同层级分组名称应保持一致的抽象维度

### 结构约束

- 分组通常控制在 3～5 个，避免首层分组过多
- 每组通常承载 2～5 个项目
- 禁止单项分组，只有 1 项时并入相邻分组
- 自定义页面优先归入"总览"或对应业务分组

## 十一、AI 助手（AI Assistant）

基于应用内数据提供智能问答、数据查询和分析建议。

### 适用场景

| 适合 | 不适合 |
|------|--------|
| 数据查询："本月库存还剩多少？" | 替代工作流执行自动化操作 |
| 状态查询："我的申请审批到哪步了？" | 代替人工完成界面操作 |
| 辅助分析："哪类图书借阅量最高？" | — |

> 结合业务中的数据查询、状态问答和辅助分析场景，按需规划 AI 助手；说明助手的具体用途，不为每个应用强行配置或添加占位对象。

知识问答和对话中的受控操作须有当前入口支持的知识资源、工具或封装流程支撑，不能仅靠提示词承诺能力。固定事件、定时自动化仍由工作流承担；资源与行为配置交助手领域落实，不扩大本次修订授权。

## 十二、打印模板（Print Template）

按打印用途、内容结构和版式要求选择模板。仅在有打印需求时选择，不作为每个应用的必建对象。

| 模板类型 | 适用需求与排版边界 |
|---|---|
| **系统打印** | 按平台标准表单版式打印记录，无自由分区或精细图文布局要求。 |
| **Word（DOCX）** | 合同、报告、公文等连续正文或动态多页文档；也适合宣传单页、复杂图文卡片等自由排版需求，不限于 A4 或长文档。 |
| **Excel（XLSX）** | 发票、收据、门票等固定字段的单页票据、套打、网格表单及多列明细。也用于制作自定义条码／二维码模板，将编码与 Logo、标题、业务字段、表格等组合排版，满足系统标准标签版式无法承载的需求。 |
| **二维码 / 条码标签** | 标准编码标签，配合编号、名称、所属单位等附加字段与说明文字；系统固定版式能够满足要求时优先使用。 |

### 选型顺序

1. **先遵循明确要求**：用户已指定模板类型时优先沿用；只有该类型无法满足目标版式时，才说明差距并建议适合的类型。
2. **判断固定版式是否足够**：标准表单或简单编码标签能满足要求时，使用对应的系统打印或标签模板；需要自由版式时再选择文件模板。
3. **按主要内容选择文件格式**：固定字段、网格对齐、严格单页的票据或套打优先 Excel；长段正文、可增长的多页文档优先 Word；复杂图文混排可选 Word。仅凭“尺寸小于 A4”“有条码”或“是发票”不强制选型，结合实际字段、明细数量和版式判断。

选型依据是打印用途、必需内容、固定尺寸或单页要求、是否套打及目标样式。指定 Word/Excel 等类型不等于明确业务用途；仅要求新增某类型模板、上下文又不足以确定用途或关键内容时，先澄清这些业务选择，再制作，不从当前表字段自行补出业务方案。用途与关键内容已明确，或用户明确委托自主设计时，直接沿用或推荐合适类型；普通排版、字段定位与文件制作交给执行器，不逐项询问，也不要求用户自行判断技术格式。

### 二维码与条形码数据源设计规范（适用于标签模板及 Word / Excel 文件模板）

- **无需预置专用字段**：打印模板是在打印生成时动态渲染码图，**均无需在工作表预先建有条码/二维码类型的字段**；使用已有的文本、自动编号等业务字段或系统记录 ID 即可动态生成。
- **二维码**：支持将**记录链接**（系统直达访问或公开分享链接）或**工作表字段**编码为二维码。
- **条形码（Code 128）**：支持将**工作表字段**（业务字段或系统字段）编码为条形码，不支持记录链接。

## 十三、外部门户（External Portal）

外部门户是客户、供应商、合作方等非本组织成员访问应用的受限入口。存在外部协作需求时才规划，不因应用有客户或供应商数据就自动开放门户。

- **先确定外部业务边界**：明确服务对象、可访问的应用项、本人或所属企业的数据归属、允许的操作。邀请、审批等准入方式解决“谁能进入”，手机号、邮箱等登录方式解决“如何认证”，角色权限解决“进入后能看什么、做什么”，三者不能互相替代。复用用户已确定的业务范围，只澄清必要缺口。
- **以可用门户为目标**：名称、基础外观、准入与业务权限应符合当前用途，不能把技术初始化当作设计完成。旧配置按本次设计目标核对，规划门户不代表已获准实际开放；仅启停或已有状态已满足本轮要求时，不套用完整设计检查。
- **以最终效果验收**：只读需覆盖相关写入入口，数据归属和角色组合共同决定有效访问；页面可访问不等于交互只读。账号开通、角色配置与真实登录验证是不同的交付结果。
- **保留执行器的设计空间**：总体方案明确业务目标和验收边界，素材、布局与配置参数由相应执行器落实；品牌素材缺失不阻塞普通外观设计，视觉选择不推导访问政策。具体能力以当前入口为准。

## 十四、物理索引（Index）

围绕明确的查询性能或唯一性要求设计索引，不为每张表默认配置。

- **普通索引**服务稳定、高频的筛选和排序；复用适用的已有索引，避免重复或过多索引，不承诺创建后所有查询都会提速。
- **唯一索引**用于已明确的字段组合唯一性约束，会限制后续写入；不能仅为提速或因字段名含“编号”而添加。
- 交接高频查询条件、排序方式或唯一性目标即可。字段顺序、配额和适用的数据检查由工作表执行器按 `hap-domain-worksheet-index-spec` 完成，主 Agent 不重复探查。

## 十五、公开表单（Public Form）

公开表单用于向外收集工作表记录。持续登录、查看和处理本人业务记录适合外部门户；独立页面与自定义交互超出原生表单时，再按网站需求选择入口。

- 按收集目的、填写对象和提交结果确定最小必要字段；内部处理字段不因存在于工作表就公开。
- 启用时交付可用的收集表单，复用合适的既有设计；基础文案、封面与填写/提交设置交公开表单执行器落实，不要求主 Agent 预先逐项设计。
- 公开表单与工作表内部表单是独立配置。查询链接、启停或局部改外观等明确任务不重做完整方案；已明确的用途和填写要求直接复用，不另设固定问答。

## 跨模块闭环设计

应用设计中，视图、字段、工作流、自定义动作之间存在强依赖关系。任何一环缺失都会导致功能无效。设计时必须确保以下闭环完整。

### 1. 工作流数据闭环

逐条检查目标需要的以下业务结果；它们是检查维度，不是所有流程必须具备的节点清单或固定执行顺序：

1. 更新主表状态
2. 更新关联表统计或状态
3. 新增流水/日志
4. 发送通知

必要数据处理成功后才能设置完成状态或发送成功通知；失败路径不得继续宣称成功。纯提醒不强制写入，已有字段计算或其他流程负责的联动避免重复执行；需要写入的流程不能仅发送通知而遗漏数据处理。

### 2. 视图 ↔ 字段闭环

视图的筛选条件必须有对应的字段和选项值支撑。

* ✅ 正确：规划了“超期事项(Table)”视图，状态字段包含“已超期”选项：`"事项状态(SingleSelect:待分解/办理中/已完成/已超期/已归档)"`
* ❌ 错误：规划了“超期事项”视图，但状态字段只有 `"事项状态(SingleSelect:待分解/办理中/已完成/已归档)"`——缺少“已超期”选项，视图无法筛选

### 3. 字段 ↔ 工作流闭环（时效性状态）

当状态字段中存在系统自动判定的选项（如“已超期”“已逾期”“已过期”），该选项无法由用户手动设置，必须有对应的工作流自动标记。

* ✅ 正确：状态字段有“已超期”选项，同时规划了一条 `date_field` 触发的工作流：“完成时限到达时，若事项状态不是已完成，则自动更新为已超期并通知责任人”
* ❌ 错误：状态字段有“已超期”选项，但没有任何工作流来自动标记——该选项永远不会被设置，视图始终为空

典型实现模式：
* `date_field` 触发 → 完成时限到达时，检查是否已完成，若未完成则更新状态为“已超期”
* `schedule` 定时触发 → 每日检查所有未完成记录，将超过完成时限的标记为“已超期”

### 4. 自定义动作 ↔ 字段 ↔ 工作流闭环

自定义动作的前置条件和执行结果都必须有字段支撑，状态变更必须有工作流执行。

* ✅ 正确：“归档”按钮的启用条件为“事项状态=已完成”，点击后触发工作流将状态更新为“已归档”
* ❌ 错误：“归档”按钮没有设置启用条件，任何状态下都可以点击归档，导致未完成的事项也可被归档

### 5. 自定义页面 ↔ 视图 / 字段闭环

工作台中内嵌的视图组件和仪表盘中的图表都依赖工作表字段的完整性。

* ✅ 正确：仪表盘中“超期事项数(numberChart)”指向事项表，筛选条件为“状态=已超期”，字段和工作流均已配套
* ❌ 错误：仪表盘有“超期事项数”图表，但状态字段没有“已超期”选项，也没有工作流标记超期——图表始终显示 0

地图图表的字段闭环：
* `regionMap`（国内地区分布）→ 工作表必须有 `Region` 类型字段
* `worldMap`（全球地区分布）→ 工作表必须有 `Location` 类型字段
* ❌ 工作表无 `Region` / `Location` 字段时，禁止规划地图类图表

## 产出质量要求

AI 在设计时应满足：

* 字段：按 8 个维度补齐业务骨架，不滥用 `Text`
* 视图：先有默认 `Table`，再按任务补高价值视图
* 图表：每个图表都回答一个具体业务问题
* 工作流：每条流程尽量形成数据闭环
* 自定义动作：优先判断是否真的需要人工点击与输入
