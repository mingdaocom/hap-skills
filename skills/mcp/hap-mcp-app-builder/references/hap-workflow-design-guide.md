# HAP 工作流设计指南

## 适用范围与完整性

- 新建或整体重构工作流时，先形成覆盖触发、处理和业务结果的完整设计。局部修订时检查目标及受影响的上下游链路，保留无关配置，不要求重做整流。
- 业务描述是意图，不是完整节点清单。实现目标必需的查询、关联表写入、状态回写、数据校验和异常处理，即使未逐项列出，也必须设计；不能把“用户没提到”当作省略必要步骤的理由。上游输入（Plan / intentHints / requirements）不含详细工具契约与实时字段类型，其中的节点选型、数据引用或计算方式若与真实表结构或平台模型不符，必须按真实字段类型、关联归属和本指南纠正为最简合法设计，不机械照搬字面措辞。
- 必要性按业务目标、数据关系及已确定的规则判断。例如入库入账不仅更新单据状态，还应沿明细与库存的依赖完成实际入账；不能只做最后的状态更新而遗漏数据处理。
- 审批、通知等需要逐项评估，并落实目标要求的处理；不因场景常见就凭空决定审批层级、金额阈值、接收范围或额外业务功能。必要依赖或业务政策不明确时标明缺口，不猜测替代、不删除必要步骤伪装完整。
- 流程索引用于区分职责，不代表其他流程已经建成或执行；保留当前目标必要的触发与衔接，不引用其他流程的运行时节点。
- 本指南定义业务设计原则和节点表达，不规定调用方的输入输出包装、调度、用户确认或发布授权。具体交接和缺口处理遵循调用方约定，物理执行遵循 hap-domain-workflow-spec。

## 设计维度

新建或整体重构必须逐项检查以下全部 7 个维度；检查后可判断某项不适用，不要求每个维度都添加节点或输出分析文字。局部修订检查受影响维度及其依赖，不以最小变更为由留下断开的业务链路。

1. **触发时机与前置条件（防死循环与误唤醒）**：
   - **工作表事件（`worksheet_event`）**：明确事件类型（新增/更新/新增或更新/删除），各时机均可设置触发条件；涉及更新时通常应指定监听的修改字段；下游回写当前表时，核对回写是否会再次满足触发条件。监听字段与回写字段重叠时，必须有明确的状态迁移、幂等条件或退出条件，不能仅凭指定监听字段就认定不会循环；
   - **日期字段触发（`date_field`）**：明确基准日期字段与相对时间偏移；在提醒、催办或阶段流转场景中，通常应设置业务状态过滤（如排除已完成、已取消记录），避免对已完结数据产生误唤醒或无效通知；
   - **定时流程（`schedule`）**：明确执行周期与时刻，仅在必要时安排查询。
2. **主表更新**：目标状态、完成时间、操作人等是否需要回写；成功状态应在必要业务操作完成后设置。
3. **关联表联动**：沿数据和业务依赖检查直接及间接影响，直到必要链路闭合；不能仅停在一层关联。检查明细变化对主表汇总/状态的影响、主表对明细的影响，以及库存/占用/可用数量等跨表结果；已有公式或其他流程负责时避免重复写入。
4. **审批**：是否需要人工审核，审批对象、发起人、审批人、通过/拒绝后的处理是否齐全；已有政策必须落实，未明确的审批政策不能猜测。
5. **分支**：业务情况、条件优先级、默认路径及汇合后数据是否可用；每条必要路径都要有明确结果。
6. **通知**：哪些结果需要告知谁、采用什么渠道、接收者能否识别事项并继续处理；不能只因未显式写“通知”就跳过评估，也不机械加通知节点。
7. **异常**：查询为空、数据不足、状态不符、重复触发、批量部分完成时如何处理；失败或未完成路径不能继续标记业务成功，避免重复扣减、入账等副作用。

## 支持的节点类型与选型

以下目录覆盖本轮已核对的沙盒 MCP 创建节点 Schema 中的 30 种类型；不同部署版本的可用类型以实际入口为准。目录覆盖类型及设计约束，不代表任意配置、形态转换或当前执行器的所有操作均可用。具体字段与可执行操作以当前工具 Schema 和调用方能力为准；本节不增加调用方的触发类型。

| type | 业务用途 | 数据来源与结果 | 关键设计约束 |
|---|---|---|---|
| `get_single` | 查询单条记录 | 工作表和筛选条件 → 单条记录 | 明确匹配范围及未找到时如何处理，不把单条查询当批量结果 |
| `get_multiple` | 查询多条记录 | 工作表和筛选条件 → 记录集合 | 下游区分集合统计与逐条处理；需要判空分支时先统计数量 |
| `get_related_record` | 从关联记录中获取一条 | 上游单条记录的关联字段 → 最多一条符合条件的记录 | 可配置过滤条件；有多条符合时可按排序取一条，或随机取一条；明确未找到时的处理 |
| `get_multiple_from_field` | 从关联记录中获取多条 | 上游单条记录的关联字段 → 符合条件的记录集合 | 可配置过滤条件、排序和返回数量上限；下游按需求逐条处理或汇总 |
| `get_single_from_multiple` | 从已有多条结果中取一条 | 上游多记录结果节点 → 单条记录 | 来源须为多记录结果，不接受单条或已删除数据来源；可再筛选、排序或随机取一条，明确为空时的处理；能直接单条查询时不必先查多条 |
| `add_record` | 新建单据或流水 | 目标表及字段值 → 新记录 | 必填数据有来源，重复触发时避免重复创建 |
| `update_record` | 更新记录或状态 | 已定位的记录/集合及字段值；无记录字段输出 | 下游需要写后实际值时重新查询，成功状态在必要操作完成后设置；只写入具有记录值写入能力的字段，计算/衍生字段由来源数据驱动（见下文「更新目标字段防护」） |
| `delete_record` | 删除指定记录 | 已定位的目标记录/集合 | 属于数据删除，不用于修复工作流节点；须符合任务范围及执行器开放能力 |
| `find_and_update` | 查找并更新一条记录 | 工作表 + 非空筛选 → 被更新的单条记录 | 定位与写入一步完成，可替代“get_single + update_record”；明确多条符合时的排序、未找到时停止或继续，下游读取更新后还是更新前的数据 |
| `find_and_delete` | 查找并删除一条记录 | 工作表 + 非空筛选 → 默认无记录输出 | 属于数据删除；明确排序、未找到处理及是否彻底删除；下游需要被删记录数据时才保留记录输出 |
| `find_and_batch_update` | 批量更新符合条件的记录 | 工作表 + 筛选 + 统一字段值 → 无逐条结果 | 所有命中记录写入相同的值或清空时使用，仅支持覆盖与清空；明确数量上限与排序，避免截断遗漏 |
| `find_and_batch_delete` | 批量删除符合条件的记录 | 工作表 + 筛选 → 无记录输出 | 属于批量数据删除，筛选范围必须准确并评估数量上限与是否彻底删除；不能以空筛选代替明确范围 |
| `branch` | 按条件分流 | 上游可用数据 → 不同执行路径 | 至少两条路径（paths ≥ 2）；筛选逻辑严格遵循外层 OR、内层 AND 两层限制，**严禁在 AND 之下再嵌套深层逻辑组** |
| `rollup` | 汇总数量、金额等 | 集合计数、工作表直查记录数，或字段聚合 → 统计值 | 区分记录计数与字段聚合；计数来源必须是接口支持的多记录结果，不能将 get_single 当集合。直查、筛选及聚合方式遵循当前工具能力，保持统计口径与覆盖范围 |
| `compute` | 数值或日期运算 | 已有数值/日期 → 计算结果 | 仅用于数值或日期计算，不能拼接文本（文本拼接直接在通知/赋值模板中完成）；明确单位、时间语义及后续用途；计算结果不等于已写回记录 |
| `update_process_variable` | 更新流程参数值 | 已定义参数 + 赋值来源 → 当前流程参数值 | 参数定义与运行时赋值分开 |
| `delay` | 等待时长或指定时刻 | 时间条件 → 延后继续 | 等待后原数据可能过时，必要时重新确认状态再执行 |
| `terminate_process` | 提前结束当前流程 | 无输入 → 流程终止 | 仅用于必须阻止后续节点执行的提前终止；无需处理的空路径不添加此节点；终止前不能已写入成功状态，后续节点不再执行 |
| `send_internal_notice` | 发送站内消息 | 接收者及文案，无需记录来源 | 接收者可来自应用角色、固定人员、触发人及接口支持的部门/职位/组织角色或动态人员来源；仅字段来源需要按人员字段语义校验，不把手机号、邮箱或整条关联记录当人员身份 |
| `cc` | 抄送记录详情 | 单条记录及接收者 | 集合需要逐条抄送时使用子流程，不能直接传多条记录；接收者遵循与站内通知相同的身份来源规则 |
| `send_email` | 发送邮件 | 接收者及邮件内容 | 明确收件范围和动态内容来源，身份与地址来源见「通知设计」 |
| `send_sms` | 发送短信 | 短信正文或已有模板 + 变量取值 + 接收者 | 默认在节点内新建模板，接收来源、签名及发送条件见「通知设计」 |
| `code` | 自定义数据处理 | 明确输入 → 声明的输出 | 现有节点不能表达时使用，明确输入输出与异常；不把外部请求默认改写成代码 |
| `webhook` | 发送 HTTP 请求 | 请求目标和数据 → 接口响应 | 区别于同名触发器；明确成功判定、失败处理及重试的业务影响 |
| `json` | 解析上游 JSON 数据 | 产出 JSON 字符串的上游记录引用 → 解析结果 | 输入须能表达为上游记录引用；根据真实响应确定下游取值，不虚构字段路径 |
| `approval_block` | 组织完整审批流程 | 被审批记录 → 最终审批结果 | 内部包含至少一个 approve，可安排填写等处理；详细审批信息在内部使用 |
| `approve` | 人工审批 | 审批对象与审批人 → 审批结果、执行人及意见 | 仅在审批块内部；通过/拒绝、会签/或签等按业务政策设计 |
| `fill_in` | 人工填写 | 记录、填写人与可填字段 → 人工提交后继续 | 仅在审批块内部；明确谁填写、哪些字段及后续读取来源 |
| `sub_process` | 封装单次或逐条处理 | 目标记录/集合与显式入参 → 内部执行 | 单次、并行逐条或串行逐条按依赖选择；明确是否完成后继续主流程，内部数据不能直接跨作用域引用 |
| `loop` | 按次数或条件重复执行 | 循环次数或退出条件 → 重复执行循环体 | 固定次数需明确起止与步长，条件循环需明确退出条件；均须设置最大循环次数并说明单次出错时继续、跳出还是终止流程；按记录逐条处理优先用 sub_process |

### 记录获取方式的选择

先确定查找范围，再决定取一条还是多条。涉及关联时，确认关联字段实际在哪张表、指向哪张表。

| 查找范围 | 取一条 | 取多条 | 示例 |
|---|---|---|---|
| 来源记录的某个关联字段已关联的记录 | `get_related_record` | `get_multiple_from_field` | 从订单的“关联商品”中筛选在售商品 |
| 目标表中，通过关联字段指向来源记录的记录 | `get_single` | `get_multiple` | 在订单明细表查询“所属订单关联了当前订单”的明细 |
| 目标表中，符合其他业务条件的记录 | `get_single` | `get_multiple` | 按订单编号查一条订单，或查所有待发货订单 |

四种方式都可进一步筛选。两边都有关联字段时，业务明确要求处理“当前记录已关联的记录”，优先沿来源关联字段获取；不能未经核实就认为两条路径的记录范围相同。取一条时，多条符合条件须明确选择规则；取多条时，说明全部符合还是排序后的前若干条，不能随意取第一条代替批量处理。

设计交接使用已有节点字段，不增加输出字段，也不写 MCP 参数：

- **`type`、`worksheet`、`dataSource`**：写所选节点类型、目标表及取数来源。例如 `dataSource` 写“触发订单的关联商品”，或“查询订单明细表，匹配触发订单”。只有需要区分数据变化前后时，才在此注明取数时点。
- **`condition`、`label`**：筛选条件写入 `condition`，如“状态为在售”或“所属订单关联了触发订单”；排序、数量范围和无结果时的处理写入 `label`，如“按价格升序取一条，未找到时结束”。需按空结果分流时，按下文规则设计相应节点。
- **下游节点的 `dataSource`**：引用获取节点的结果；子流程逐条处理时引用当前遍历记录。更新、通知或汇总用途由对应节点及其业务字段体现。

### 外部请求与解析

- 设计前确认外部接口用途、请求输入、响应样例或契约，以及结果在后续业务中的用途；资料缺失则标记依赖，不编造地址、认证信息、响应字段或假设任意字符串都可作为 json 输入。
- HTTP 请求成功不必然代表外部业务成功；按接口契约检查业务结果。只有下游需要解析 JSON 时才安排 json 节点，不为每个请求机械追加解析。
- 需要声明请求方式、数据来源、响应消费方式等设计信息时，写在对应节点的自然语言说明中，供执行器映射当前 Schema；不自行新增 Blueprint 顶层包装。
- 请求失败、解析失败或返回缺少关键结果时，按目标选择停止、记录异常或通知；不能继续写入成功状态。会创建订单、扣款等的请求不能默认重试，先确定外部接口的幂等或查重机制。
- webhook 节点的自行配置请求与沿用已有请求节点属于不同模式，原地切换不保证支持；修订时保留既有模式，能力不支持时报告缺口，不自动删除重建。

### 自定义动作的数据源选型

- 直接触发与表单提交后触发均需完整设计后续业务节点。表单输入从提交后的真实记录字段读取，不虚构“本次动作输入”参数；新建关联记录时区分动作所在记录与新建记录，依据关联和实际触发来源取数。后续流程不能假定保留字段修改前的值，需要原值时须有明确保存来源。
- 直接触发动作的单数据源 `single` 在多选入口按记录分别触发流程；多数据源 `multiple` 由一个主流程处理选中集合，也可从详情/行内入口处理一条。创建时按业务选择，与按钮入口独立；既有动作的触发数据源固定，切换须按动作领域规范删除并重建动作，不能设计为原地修改触发节点。
- 各记录独立计算、审批、通知或派生台账时优先 `single`；多条合成一张主单、集合统一更新/删除、汇总后集中报送时选 `multiple`。合单可新建主单并通过支持多条的关联字段绑定触发集合，保留业务已确定的合并条件。
- 仅当集合任务还需共享上下文逐条处理时组合 `multiple + sub_process`，如先建汇总主单、再逐条生成其明细、最后统一通知；不为独立逐条操作套一层批量主流程。
- 一个主流程实例不等于只发送一条消息或一次外部请求；按实际收件人、消息内容与接口契约设计汇总通知，不承诺固定耗时、无限条数或自动容错。

### 子流程执行方式

- 单次处理一组步骤时可选择单次执行；多条记录互相独立时可并行逐条，有顺序依赖或会竞争同一份业务数据时选择串行或明确协调方案。子流程用于遍历多条记录集合或封装多步处理；单条记录上的多选人员/部门/组织角色字段不是记录集合，发送相同通知或统一赋值时直接用单个节点处理，不因上游“逐条/分别通知”措辞拆成 `sub_process`。
- 主流程需要在明细全部处理后汇总、标记完成或通知成功时，必须明确内部完成后继续，不能依赖默认设置。不需要继续时明确结束位置。
- 遇错继续属于业务选择，不代表所有条目成功；部分失败时保留失败项，主流程不得无条件标记整体完成。

### 批量写入、循环与提前结束

- **批量更新/删除**：已有目标集合（如多数据源动作的选中记录）统一写入相同值、清空字段或整体删除时，直接用 `update_record` / `delete_record` 消费集合；需要按条件从工作表查找目标时用 `find_and_batch_update` / `find_and_batch_delete`，不以重新查询整表替代用户选中范围，也不为统一处理增加子流程。集合内确需差异计算、逐条审批或多步处理时才逐条展开；自定义动作按上节选型。批量写入节点不产出逐条记录，后续统计或通知复用有效来源，仅确需写后实际值时另行查询。
- **单条查找并写入**：只为定位一条记录后立即更新或删除时，可用 `find_and_update` / `find_and_delete` 减少节点；需要先判断、分支或复用查询结果给多个下游时，保留独立查询节点。
- **循环**：`loop` 用于按次数重复、重试或直到条件满足为止；循环体是独立作用域，固定次数明确起止与步长，条件循环明确退出条件；两者都设置最大循环次数及出错处理，防止无限执行或重复写入。逐条处理一组记录不用 loop 模拟遍历。
- **提前结束**：只有业务明确要求提前终止当前流程、阻止后续节点执行时才用 `terminate_process`。无需处理、不满足处理条件或无数据可处理的路径保持无动作，正常汇合或自然结束，不为“无需处理，流程结束”增加中止节点。区分跳过当前分支动作与停止整个当前流程，避免误阻断汇合后的必要步骤；终止路径上不能已写入成功状态。

## 数据来源与状态

- 可按业务需要使用流程参数。在流程 `description` 中说明参数名称、类型和用途，赋值步骤使用 `update_process_variable`，取值来源和使用位置写入现有 `nodes` 字段。
- 每个读写节点明确目标表、记录来源和字段来源。触发记录、当前遍历记录或上游已有可用记录可以复用；其他记录需要查询定位。定时流程只有在需要记录时安排查询。
- **Lookup 展示与流程取值分开设计**：工作流新建或修改取值不直接引用 Lookup，应沿关联关系设计必要查询并使用真实来源字段，已有有效来源记录直接复用。设计中明确记录范围、业务取值时点及缺失处理；类型校验与具体引用由执行器按工作流领域规范落实。
- update_record 没有输出。后续使用原始值时引用触发/查询节点；需要写入后的实际值时重新查询，不把更新节点作为数据源，也不假设旧查询自动刷新。
- **更新目标字段防护**：更新目标须具有记录值写入能力；他表字段（Lookup）、数值公式（Formula）、文本组合（Concatenate）、自动编号（AutoNumber）、汇总（Rollup）、日期公式（DateFormula）、条码/二维码（Barcode）、函数公式（FunctionFormula）等衍生字段以及纯布局/展示控件不能直接赋值。需要改变计算结果时，按原业务目标更新可写来源字段，不能擅自删除必要更新或改造字段类型。执行器依据真实字段类型与当前写入契约映射，界面可编辑性不能替代接口可写能力。
- **条码/二维码的来源驱动**：生成或改变条码内容应由其实际引用来源驱动；已知可写来源时设计对来源的赋值，已有来源和生成配置满足目标时无需额外的“写条码”步骤。设计输入缺少来源配置时保留目标值与业务效果，明确交由执行器核实实际引用后等价实现，不猜来源名称、不把待查配置直接判成能力缺失。这不属于改变业务目标的替代方案；同一操作中的其他必要更新仍须保留，发送完成标记不能提前设置。
- 状态流转须符合目标与已有业务顺序，必要的时间、操作人、关联数量回写在范围内一起设计；不自行发明状态或审批政策。
- 选项使用对应字段 options[].value 中准确的名称，物理执行时再映射 key。没有准确匹配时报告缺口，不选择“语义最接近”的值代替。

### 条件设计规则

- **条件语义与类型兼容**：条件两端对象必须语义与类型兼容，关联字段表示关联记录引用（可能多条），不是记录名称字符串，不能与普通文本字段直接等值比较；使用目标表的关联字段与来源记录 ID 比较，是判断该字段是否关联了这条来源记录，关联字段须指向来源表。不能反过来把来源记录的关联字段当作目标记录 ID。普通单行文本仅设计等于、不等于、包含、为空等基础判断，不设计多值集合匹配。
- **明确匹配含义**：关联条件写清“是某条记录”“包含某条记录”或“包含全部指定记录”，避免只写含糊的“属于”；部门、地区是否包含下级是另一种业务要求。匹配记录 ID 与匹配标题文本要区分，具体操作符和参数结构交给执行器。
- **读取关联记录的文本属性**：比较名称以外的文本属性时，先复用已有可用的关联目标记录，缺少时按前述获取方式取得目标记录，再比较其真实文本字段；不要把关联字段本身当作该属性。仅匹配关联记录标题且当前工具支持标题比较时可直接设计标题条件，无需机械增加查询。多条关联按业务范围逐条判断或筛选，不能任意取一条。
- **两层逻辑限制**：工作流筛选条件仅支持最外层「或」、内层「且」两层逻辑，**严禁在「且」条件组下嵌套深层子逻辑组**。

### 汇总统计设计规则

- **记录数量统计（`count`）**：
  - 明确筛选条件、去重口径及是否按分组统计；优先复用已有完整记录集合。需要查询时使用 `get_multiple` 或其他接口支持的多记录来源，再计数；不能将 `get_single` 当集合，也不能把分页/截断结果的条数当总数。
  - 当前工具明确支持工作表直接计数时可用单节点实现，减少查询；设计器只交接统计口径，不预设物理参数，由执行器按当前契约选择实现。
- **字段级数值聚合与填报完整度**：明确目标字段、筛选范围与求和/均值/极值等口径。已填/未填是筛选后计数的业务要求，不预设 `filled` / `not_filled` 为合法方法名；执行器按当前工具能力实现。

## 分支与内部作用域

- **流转顺序与数据来源分开**：branch 及其路径只决定后续执行路线，不产出业务字段。下游节点的 dataSource 与条件取值仍指向实际提供数据的触发、查询或具有所需输出的节点，不能因紧跟分支就改成“来自分支”。汇合后只使用该执行路径确实可用的数据，不借用未经过的兄弟路径输出。
- branch 至少 2 条路径（paths ≥ 2）；只有一种业务条件时保留默认空路径，正常汇合或自然结束，不添加占位动作或 `terminate_process`。
- 仅在业务需要对查询空结果分流时安排判空分支：get_single/get_related_record 判断是否取得记录；get_multiple/get_multiple_from_field 先 rollup(count)，再判断数量。查询的空值处理必须允许到达该分支，不能先停止再安排空值路径。
- 多条记录需要逐条审批、抄送或逐行处理时使用 sub_process，不把集合当单条记录。
- 子流程是独立作用域。当前遍历记录及内部查询可直接使用；只有其他外层节点的数据才标注「外层」及来源，由执行器创建流程参数桥接。不要把当前记录字段重复当作外层参数。
- 审批块内部使用被审批记录或内部查询，不使用子流程的「外层」引用机制；父流程不能直接引用内部节点。
- 审批块明确审批对象、发起人和审批人，内部至少一个 approve；会签/或签/依次审批及是否允许拒绝由业务政策决定。
- 父流程在 approval_block 后判断最终 PASS/OVERRULE。需回写实际审批人或意见时，在内部 approve 后通过审批结果分支处理，使用该审批节点的 executorid / opinionSummary；不要在父流程引用内部审批节点。

## 通知设计

- 仅设计目标需要的通知，准确指定接收者和来源，例如「字段：负责人（查询客户节点）」或「角色：仓库主管」，不写“相关人员”让执行器猜测。
- **接收者范围与角色定义**：
  - **应用角色（推荐群发）**：设计指定「角色：仓库主管」等业务角色时，对应应用内的角色定义，由执行器映射为真实角色；
  - **工作表身份字段**：指定字段及来源节点（如「字段：负责人（触发记录）」），按对应渠道支持的字段类型配置；站内通知可使用人员、部门或组织角色字段，不将组织角色字段与应用角色混淆；人工节点的执行人等系统人员输出按其专用契约引用；
  - **系统触发人与固定身份**：触发人使用运行时来源；指定人员、部门、职位或组织角色前，应区分“节点支持该身份”与“调用方能解析其 ID”。只有已有可靠 ID 或执行器具备对应组织范围内的查询能力时才作为可执行来源，名称解析交给执行器；无解析能力时标明依赖，不将字段类型限制套到固定身份上；
  - **字段类型禁令**：站内通知或抄送的接收者不能使用手机号码、电子邮箱、普通文本或整条关联记录；
  - **短信与邮件的接收来源**：两者都支持人员、部门、组织角色、职位、应用角色及触发人。平台还支持短信使用固定手机号、手机/文本字段，邮件使用固定邮箱、邮箱/文本字段；联系方式字段不套用人员字段限制，短信文本字段需包含手机区号。
  - 对外部人员：原目标允许邮件且有真实邮箱时设计 `send_email`；允许短信且有真实手机号来源时设计 `send_sms`；通知内部对接人仅可作为已授权的替代方案。缺少可用渠道时标明依赖，不擅自更换收件人或假定已有邮箱/手机号；
  - 外部门户角色不能直接作为 cc/send_internal_notice 的角色接收者；人员字段或邮件替代也须符合已确定的收件范围和渠道。
- cc 发送单条记录详情；send_internal_notice 用于不关联记录的站内消息；send_email 用于邮件渠道；send_sms 用于短信渠道。单条记录的多选人员/部门/组织角色字段直接由单个通知节点群发；仅多条记录集合需逐条抄送或按行发送差异内容时使用子流程，不为单条通知或同文群发增加子流程或循环。
- **短信设计**：写出完整短信正文，动态内容用字段来源占位（如「{{触发记录.客户名称}}」），并说明用途属于行业通知、营销推广还是金融交易；用户明确指定已有短信模板时注明模板，否则不要求预先申请模板。新建模板须使用组织可用的已审核短信签名，用户指定的签名或品牌要求传给执行器，由执行器查询确认，不在设计阶段假定通用签名。变量只取上游字段值。号码支持大陆手机号及带 `+` 国家码的国际号码；港澳台/国际短信依赖组织集成相应短信服务，未确认时注明依赖，不承诺送达，也不擅自改用其他渠道。
- 写出足够识别业务事项和下一步动作的文案，使用字段名及来源占位符，如「订单 {{触发记录.订单编号}} 已完成，请核实签收」。需要其他表信息且无现成来源时再安排查询，不强制 HTML 或无关信息。

## 标准工作流设计结构

以下 Blueprint 表达工作流的业务设计，节点使用名称及明确的数据来源，由执行阶段映射为真实引用。它不是 MCP 参数格式，也不要求任何调用方新增输出包装。

系统流程可使用 name + description + trigger + nodes；自定义动作流程的触发器由动作外壳提供，可使用 name + description + worksheet + nodes。需要设计与执行交接时使用此结构；同一执行器内部设计时不要求先对外输出完整 JSON。

```json
{
  "name": "工作流名称",
  "description": "工作流业务目的",
  "trigger": {
    "type": "worksheet_event | date_field | schedule",
    "source": "触发工作表名称；schedule 可为空",
    "label": "触发时机与条件说明：worksheet_event 必须明确触发时机；涉及更新时通常进一步注明监听的修改字段（如「当新增记录且【门票类型】为VIP时」或「当更新记录且修改【审核状态】且等于审核通过时」）；date_field 注明基准日期与偏移，如需状态过滤一并注明（如「【开始时间】到达前30分钟且【议程状态】为待开始」）；schedule 注明循环周期与执行时刻（如「每天08:30定时运行」或「每周一09:00定时汇总」）"
  },
  "nodes": [
    {
      "type": "节点类型",
      "label": "节点说明（自然语言）",
      "worksheet": "目标工作表名称",
      "dataSource": "数据来源说明",
      "updates": [
        { "field": "字段名称", "value": "固定值直接写；引用其他节点字段时标注来源如「查询图书记录.库存数量 - 1」；系统值写「当前时间/触发时间/触发人」；在子流程内引用外层数据时加『外层』前缀，如「外层触发记录.客户名称」；选项用实际名称不用 key" }
      ],
      "condition": "查询或分支的条件描述（自然语言）",
      "recipients": "字段：报修人（触发记录） / 角色：物业客服 / 触发人",
      "content": "完整通知文案，用字段名占位。如：您的订单 {{订单编号}} 已提交，金额 {{订单金额}} 元。",
      "branches": [
        {
          "name": "分支名称",
          "condition": "进入条件描述",
          "nodes": [ "…可嵌套任意节点" ]
        }
      ]
    },
    {
      "type": "approval_block",
      "label": "审批流程说明",
      "dataSource": "审批对象来源（触发记录 / 查询节点名称）",
      "nodes": [
        {
          "type": "approve",
          "label": "审批节点说明",
          "approvers": "审批人描述（角色名/人员字段名）",
          "mode": "会签/或签/依次审批"
        }
      ]
    },
    {
      "type": "sub_process",
      "label": "子流程说明（对多条记录逐条执行）",
      "dataSource": "数据来源（查询多条节点名称）",
      "nodes": [ "…可嵌套任意节点" ]
    }
  ]
}
```

节点只包含与类型相关的字段；选项用实际名称，内容语言遵循调用方要求。

## 设计自检

- 新建/整体重构是否逐项检查全部 7 个维度，局部修订是否检查受影响链路？检查后不适用的维度可不新增节点。
- 从触发沿每条必要路径走到业务结果：主记录、关联记录、汇总/数量及状态是否一致？中间失败时是否仍会错误标记成功？
- 数据来源、选项名称、查询空值处理、分支可达性与父子作用域是否准确，是否错误引用 update_record 输出？
- 审批和通知是否有明确政策及人员来源，缺口是否保留并报告而非猜测？是否引入独立于目标的额外业务决策？
- 重复触发和部分完成是否可能造成重复业务写入？现有字段或其他流程已实现的联动是否被重复设计？

## 数据处理与统计口径

- 涉及数据处理或统计时，保留设计输入已明确的分组维度、时间事件、指标单位、条件与接收范围；要求分组输出时不能只给整体结果。Build 沿用上游设计，Modify 沿用已授权任务，不另造业务政策。
- 时间筛选须对应目标业务事件；业务日期、创建时间、修改时间与事件实际发生时间不自动等价。依据已有字段说明选择准确时间字段；无法确定时由具备读取能力的执行器定向核实；无工具的设计器保留目标口径及待核实项，不猜测字段。
- 筛选条件只有在等价性有证据支持时才能替换，不能仅凭字段名称或状态含义推断。计数须区分记录行数、去重实体数与组合维度下的数量；去重与分组按批准口径实现。
- 实现受限时说明未满足的口径，不悄悄降级。发布前利用已有配置与回执核对业务结果；校验通过和发布成功不代表代码运行或通知已送达。
