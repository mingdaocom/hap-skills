# HAP 角色与权限领域对象规范

本规范定义 HAP（明道云）应用自定义角色的权限分发模式、核心约束及增量/全量更新边界。创建与修改角色共用同一套权限对象结构。

---

## 角色适用范围（roleScope）

内部自定义角色使用 `general`，外部门户自定义业务角色使用 `externalPortal`；创建时按已批准角色用途明确传入，不能省略外部门户角色的范围。`roleScope` 区分角色受众，`permissionScope` 决定权限分配方式，两者不能互相代替。已有角色更新保留原 roleScope，不因同名转换类型；系统和默认门户角色继续受保护。

外部门户角色按批准的应用项、记录归属、字段和操作范围精细授权，不套用下文内部岗位的广泛默认权限；缺少必要的数据归属依据时返回缺口，不默认开放全部记录。

### 外部门户最终范围验收

- 区分“追加某项访问权”和“让某类用户只能访问指定内容/只读”。追加任务保留范围外权限；限定最终范围的任务需对照目标角色现有权限处理冲突，不能用“未新增编辑/删除权限”代替最终只读。
- 只读任务核对目标对象的记录、视图、字段及相关写入动作；签署、审批或按钮按实际行为判断，不能只看名称。页面 enable 仅代表可访问，要求页面交互只读而工具无法核实时，交回具体缺口，不擅改全局页面/按钮影响其他角色。
- 冲突旧权限在本轮范围内处理；收紧涉及未授权受众或高风险影响时交回具体范围供确认。仅在影响本轮目标时核查成员和叠加角色，不因局部角色修改全面检查所有外部用户。回执区分角色配置与用户有效权限，无法验证的部分如实说明。

## 一、 权限分发两大模式 (permissionScope)

`permissionScope`（String）决定权限分配方式，分为两大模式。**无特殊说明时，一般都应采用「模式二：分配精细权限（permissionScope: "0"）」**，按职责为角色逐项配置工作表与页面权限，以实现更专业、安全的权限管控：

### 1. 模式一：所有应用项权限（Global Permissions 模式，`permissionScope > "0"`）
仅当明确需要对角色一揽子开放全部工作表与页面时使用。角色自动获得应用内**所有工作表与自定义页面**的访问权，通过 `globalPermissions` 对象统一定义全局操作（8 项布尔值全部必填）：
- **`"80"`**：所有应用项，可查看、编辑、删除全部记录；
- **`"60"`**：所有应用项，可查看全部记录，仅可编辑/删除自己拥有的记录；
- **`"30"`**：所有应用项，仅可查看已加入的记录，仅可编辑/删除自己拥有的记录；
- **`"20"`**：所有应用项，全部记录只读。

> **约束**：此模式下，逐项精细权限数组（`worksheetPermissions`、`pagePermissions`、`chatbotPermissions`）不生效。

### 2. 模式二：分配精细权限（Per-Item Permissions 模式，`permissionScope: "0"`，默认推荐）
无特殊说明时的默认标准模式。角色按应用项逐个精准授权，`globalPermissions` 不生效，必须通过以下三个数组进行配置（至少一类包含有效授权）：
- **`worksheetPermissions`**：工作表与视图级精细权限；
- **`pagePermissions`**：自定义页面访问权限（`[{ id: pageId, enable: true }]`）；
- **`chatbotPermissions`**：AI 助手访问权限（`[{ id: chatbotId, enable: true }]`）。

## 二、 工作表精细权限核心约束 (worksheetPermissions)

每个授权的工作表对象包含记录范围、视图权限及动作配置，需严格遵循以下平台约束：

### 1. recordDataScope 范围等级约束
`read`、`edit`、`delete` 采用整数等级：`0`（无权）、`20`（本人拥有/参与）、`30`（本人及下属）、`100`（全部）。
- **逻辑约束**：`edit` 和 `delete` 的范围不得大于 `read`（无查看权限时严禁赋予编辑或删除权限）。
- **成员字段联动**：按自定义成员字段（执行人/巡检人/维修员/负责人）鉴权不在角色接口传字段名，而是将该工作表 `Collaborator` 字段设 `config.userPermission: 2`（拥有者，角色配 `read: 20, edit: 20` 即可读写）或 `1`（只读，角色 `read: 20` 可查看）；跨表按站点/项目负责人鉴权时，通过默认值（`relation`）或业务规则（`rcid`）将关联负责人同步至本表 `userPermission: 2` 成员字段。

### 2. recordPermissionInViews 视图权限（必传且极端重要）
> [!CAUTION]
> **`recordPermissionInViews` 是角色在界面各视图中的实际访问入口。如果不传此参数或传空数组，角色将无法在应用前端界面中看到该表的任何记录！**
> 必须从已验证的视图上下文或实时查询结果提取该表真实 `viewId`，为每个可访问视图传入 `{ viewId, read, edit, delete }`；若角色需访问该表全部视图，必须逐一列出该表全部真实 `viewId`。视图内的布尔权限不得超越对应 `recordDataScope`。

应用修订中新建视图时，精细权限角色不会因已有该表访问权限而自动获得新视图入口；须将已授权的新视图真实 ID 合并进目标表的 `recordPermissionInViews`，保留既有视图、字段、记录范围及操作配置。只有已核实处于上述全部应用项权限模式的角色才自动覆盖新视图，并仍受原记录范围与操作权限约束；不得为了省略逐视图授权而切换角色权限模式。已有配置满足目标时不重复写入。

### 3. fieldPermissions 字段级限制
默认传空数组 `[]`。仅在需要对特定敏感字段进行单独隐藏或只读锁定时传入 `{ id, read, edit, add, decrypt }`：
- `id` 必须为真实字段 ID 或 alias；
- 当 `read: false` 时，不得授予 `edit`、`add` 或 `decrypt`。

### 4. 动作与打印模板黑名单 (unableCustomButtons / unablePrintTemplates)
- **`unableCustomButtons`**：`string[]`，禁用的自定义按钮/动作 ID 列表。默认 `[]`（全量动作可用）；需要限制高危动作时填入其 ID；
- **`unablePrintTemplates`**：`string[]`，禁用的打印模板 ID 列表。默认 `[]`（全量模板可用）；需要限制敏感单据打印时填入其 ID。

### 5. 关联扩展权限（仅保留回写）

以下三项均为 `string[]`，存放本表关联字段的真实 ID，用于记录权限的关联扩展，不等同于普通字段的 `fieldPermissions`：

- `canReadExtendAttrs`：可读扩展权限；
- `canEditExtendAttrs`：可编辑扩展权限；
- `canRemoveExtendAttrs`：可移除（删除）扩展权限。

**用户扩展属性及其关联扩展权限暂不支持设置**。普通关联字段不等于可用的用户扩展属性，不能仅凭字段结构或名称选择、推导可用项；新增、调整或清空扩展配置均交人工处理，不因用户已授权就尝试写入，也不以放宽记录范围替代。

- 修改已有单表的普通权限时，仅原样保留 `get_role_worksheet_permission` 对该角色、该表返回的三个数组，不从其他角色或表复制。明确返回的 `[]` 是有效空配置；实际缺项不能自行补空，仍无法取得原值时停止该表权限写入。
- 增量更新省略顶层 `extendAttrs`、`optionalControls`、`delExtendAttrs`、`deloptionalControlsIds`，保留其现状；不使用 `get_role_details` 的默认空值覆盖，也不改用全量覆盖绕过。必须全量覆盖却无法取得完整扩展配置时，停止该覆盖操作。
- 新建角色不配置上述扩展属性和三个数组，省略这些可选参数。任务要求扩展设置时报告该部分暂不支持；普通权限可独立完成，但不能把扩展需求报告为已实现。

## 三、 权限推演原则与角色职能惯例

1. **基于职责描述深度推演**：根据角色 `description` 语义分配权限。若描述仅为“查阅/汇总/报表查看”，绝不能给 `edit`、`delete` 或 `add` 权限；
2. **常见职能角色配置惯例**：
   - **未在职责范围中体现的工作表**：不赋予权限（不加入 `worksheetPermissions` 或设为 `read: 0, edit: 0, delete: 0` 且 `add: false`）；
   - **普通业务操作角色（销售、内勤、客服）**：通常拥有全部记录的读取权与本人负责记录的写权限（`read: 100, edit: 20, delete: 20`，`add: true`）；
   - **部门主管/团队负责人**：通常拥有本人及下属数据的编辑权（`read: 100, edit: 30, delete: 20`）；
   - **业务管理角色（总监、运营经理）**：通常具有所有数据的写权限（`read: 100, edit: 100, delete: 20/100`），并开启导出和批量操作；
   - **只读巡查/决策角色（老板、审计、顾问）**：全局或指定表的纯只读（`read: 100, edit: 0, delete: 0`，`add: false`，关闭导入/导出/批量）。

## 四、 创建与修改的安全边界（按实际覆盖范围保护）

- **原生工具与任务边界**：按已授权任务明确目标角色及涉及的工作表、页面或助手；基本信息修改只需定位目标角色，不扩大到未批准对象。
- **按角色合并**：Agent 按需查询摘要和目标单表、合并批准差异，同角色优先合并独立变更，不逐字段或逐表派发；有依赖或修参需要时可分步执行。不同角色可并行。
- **单表权限回写**：`get_role_worksheet_permission` 的 `permission` 提供目标表的可写权限状态，完整有效时作为合并批准的普通权限差异的基线；三组关联扩展权限遵循第二节“仅保留回写”的限制。以返回的 `worksheetId` 设置 `worksheetPermissions[].id`，按当前写入 schema 提交完整单表项；响应中的名称、`navigateHide`、`canAdd`、`version` 等只读信息不透传。角色摘要或全局模式下合成的单表有效权限不能替代精细权限原始配置，也不能据此切换权限模式。仅实际缺项或响应不完整时补查，仍无法保留被覆盖配置则停止相关写入；不把未知值填成空数组，也不为已有完整单表结果例行查询整个角色。
- **保留既有权限**：职能惯例仅用于批准的新权限设计，不得借“精配”收紧修改范围外的既有动作或记录范围；用户明确限定最终范围时，与目标冲突的旧权限按上述验收规则处理，不能当作范围外权限一律保留。

- **新建角色一次提交**：`create_role` 支持同时提交角色基本信息和批准的初始权限。首次明确新建且输入完整时直接一次提交，不先查重、创建空角色、读取详情再补权限；接口明确返回成功即可使用真实 `roleId`。只有条件创建、恢复未知结果或用户要求复核时才查询角色列表/详情。

- **ID 真实性约束**：工作表、视图、字段、自定义页面、AI 助手和按钮 ID 必须来自实际已创建的对象，**严禁自行编造 ID**。
- **update_role 覆盖范围**：局部修改显式 isIncremental=true 与原 permissionScope；增量模式省略 permissionScope 同样会设为 0，不会保留原模式。原模式未知时补查摘要，已知时复用；省略其他未修改角色属性和应用项。提交的工作表与 globalPermissions 仍整体替换，未修改的字段/视图、操作开关、关联扩展权限和按钮/模板禁用名单必须保留；不回写旧 mapper 默认值。全量模式必须有完整可信快照。
- **验证与恢复**：原生响应足以确认目标变化时直接收口，证据不足才定向回读；目标已满足则无需写入。明确失败且未生效时允许修参继续，未知写入先查，部分成功只处理剩余项。逐对象如实说明完成情况。version 不是平台条件更新令牌。
- **角色范围边界**：只能操作当前应用内的自定义角色；系统预设角色（如管理员）及其他应用角色不可编辑。
- **角色成员解耦**：角色的成员分配（`add_member_to_role` / `remove_member_from_role`）属于独立操作，不随 `create_role` / `update_role` 自动配置。

## 五、成员增删

- 成员分为 `userIds`、`departmentIds`、`departmentTreeIds`、`jobIds`、`orgRoleIds` 五类；至少一类非空。
- 新增成员前按名称查得真实 ID，并检查添加接口的逐项业务响应；不为证明明确成功再读取角色列表。重名、无法唯一定位、部分成功或结果不明时才回读相关成员并停止不确定项。
- 移除成员时必须按 `get_role_list` 返回的原加入粒度操作。通过部门、部门树、职位或组织角色获得权限的人员，不能按单个 `userId` 移除。
- `remove_member_from_role` 的 `operatorId` 使用当前已认证用户的真实 ID，不得从业务文本猜测，也不得向用户展示该内部参数。
- 成员加入或移除都属于权限变化，已明确获授权的常规任务为 `low` 可 `direct`，低风险新增业务方案先说明连带影响并经用户确认后可 `direct`，高风险（`high`）必须取得 `confirmed`。

## 六、角色删除、排序与合并

- `sort_roles` 只接受当前应用全部真实角色 ID；排序时必须保留未调整角色，禁止发送局部数组。
- 修订删除授权遵循 hap-revision-safety。成员配置须覆盖用户、部门、部门树、职位、组织角色五类；系统角色、默认外部门户角色不可删除。
- delete_role 无回收站或撤销参数，不承诺可恢复；合并或含成员角色删除须解决必要成员去向与已知引用。
- 角色合并没有原子接口，必须拆成有依赖的批次：
  1. 基于目标角色完整实时配置合并批准的权限；
  2. 按五类成员粒度把源角色成员加入目标角色并回读；
  3. 迁移能够安全修改的直接引用；
  4. 再次检查源角色引用与成员去向；
  5. 仅在已确认的合并范围及前置条件仍有效时删除源角色，不重复确认。
- 任一步失败都保留源角色并返回部分成功；不得为了“完成合并”强制删除仍被引用的角色。
