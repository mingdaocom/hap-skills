# HAP 应用视觉主题、导航与图标规范

本规范定义 HAP（明道云）应用实体基础属性、视觉主题配色、导航栏风格与布局形态、受控图标库以及描述文本规范。创建应用（`create_app`）与修改应用（`update_app`）共用同一套领域属性标准。

---

## 一、 应用基础属性与平台契约

应用（Application）是组织内各类业务工作表、自定义页面与工作流的顶层聚合容器：

- **`name`**（String，必填）：应用名称。
- **`orgId`**（String，必填）：所属组织 ID。
- **`color`**（String，可选）：应用主题色 HEX 格式（推荐从黄金 9 色板中选取，如 `"#3054EB"`）。
- **`icon`**（String，可选）：应用主图标文件名（必须来自受控图标库，如 `"sys_app_symbol"`、`"sys_18_5_warehouse"`）。
- **`navColor`**（String，可选，默认 `"appColor"`）：导航栏颜色风格枚举（见第二节，**严禁自定义 HEX 色值**）。
- **`navLayout`**（String，可选，默认 `"group"`）：导航布局形态枚举（见第三节）。
- **`enableExternalPortal`**（Boolean，可选，默认 `false`）：是否开启外部门户。
- **`group`**（String[]，可选）：应用所属组织内分组 ID 数组（传入如 `["<groupId>"]`）。
- **`remark`**（String，可选）：面向开发者/AI 的一句话应用定位描述。
- **`desc`**（String，可选）：面向终端用户的富文本使用手册。必须使用**原生 HTML + 行内 CSS**（支持 `<h3>`、`<p>`、`<ul><li>`、`<strong>`、`<br>`、带样式 `<div>`，详见第六节），严禁 Markdown 与 `&lt;p&gt;` 转义实体。

---

## 二、 黄金 9 色板主题配色规范 (color)

推荐使用以下 9 种精选的 HAP 官方主题配色，具有良好的视觉质感并保证反白文字的可读性。避免使用纯红（`#FF0000`）、纯绿（`#00FF00`）等非受控低质感色值：

| Hex 色值 | 配色名称 | 视觉感知与推荐业务场景 |
| :--- | :--- | :--- |
| **`#3054EB`** | **科技蓝** | 通用且稳重的主力配色。适用于核心业务流水、综合看板、工作量统计（**默认推荐**）。 |
| **`#4051B6`** | **商务深蓝** | 严谨的 HR 组织架构、合同档案、系统配置表、权限后台。 |
| **`#732ED1`** | **睿智紫** | 人工智能、高新技术、战略规划、创意设计、前瞻性业务系统。 |
| **`#21710F`** | **生态绿** | 环境保护、农业技术、供应链生命周期、企业健康度等。 |
| **`#4CAF50`** | **清新绿** | 敏捷任务状态、日常轻量审批、用户自助服务。 |
| **`#FC532E`** | **温暖橙** | 物流配送、现场服务、敏捷运营看板、警示提醒。 |
| **`#F21B65`** | **活力粉** | 时尚、零售、社交娱乐、以客户体验为核心的协同板块。 |
| **`#A00416`** | **典雅红** | 风险控制、安全合规、高优先级的核心金融或生命科学模块。 |
| **`#8E481B`** | **质感棕** | 历史档案、物资仓储、重型设备管理、公共资源归档等。 |

## 三、 导航栏配色方案 (navColor)

`navColor` 决定左侧/顶部导航栏的底色风格，只能从以下 4 个官方受控枚举值中选择（**系统不支持自定义 HEX 色值**）：

| 枚举值 | 说明 | 适用场景 |
| :--- | :--- | :--- |
| **`appColor`** | 导航栏使用应用主题色（暗色系） | 蓝、绿、紫等深色主题应用（**默认推荐**） |
| **`white`** | 导航栏白色背景 | 红、橙、黄等亮色暖色系主题应用 |
| **`gray`** | 导航栏灰色背景 | 中性、低对比导航场景 |
| **`black`** | 导航栏纯黑背景 | 重工制造、监控中心、品牌工作台等少数场景 |

---

## 四、 导航布局形态 (navLayout)

根据应用的业务结构复杂度与页面层级选择适合的导航形态：

| 形态枚举 | 说明 | 适用业务类型 |
| :--- | :--- | :--- |
| **`group`** | 默认分组导航（左侧经典列表） | ERP、CRM、WMS、OA 等典型业务系统（**默认推荐**） |
| **`tree`** | 树形多级导航 | 结构复杂、分类层级深（如多级组织架构、多级科目/分类） |
| **`top`** | 顶部水平导航 | 多业务域并列、门户型大屏看板、表单数量极少（≤ 4 个）的轻量工具 |
| **`card`** | 卡片式导航 | 首页入口导流型工作台应用 |

## 五、 受控图标选择规范

配置应用、工作表、自定义动作、导航项或自定义页面的 `icon` 属性时，必须从官方受控图标精选板 `skills/hap-icon-palette` 中选取精确的 `fileName`（如 `"sys_app_symbol"`、`"sys_18_5_warehouse"`），**严禁凭空捏造图标名称**。

### 图标与样式设计准则

1. **业务语义优先**：图标的设计表意必须贴合实际应用或功能模块的业务定位（如客户管理→人物类、资产仓储→仓库类）。
2. **同组避免雷同，跨组业务优先**：同一导航分组（`groupName`）内各元素 icon 尽量不同；不同分组之间可依据业务贴合度复用，不强求全应用零重复。
3. **色彩层级适度打散**：方案规划时，同组元素使用相近色系，不同业务组之间拉开色系层次，避免整站单调。
4. **严格受控**：仅使用白名单中的受控文件名（保留 `sys_` 前缀与原有大小写）。

## 六、 应用说明（remark）与使用手册（desc）生成与修订规范

本节定义 `update_app` 写入应用 `remark`（AI 描述）与 `desc`（使用手册）的标准规则，供应用创建及修订阶段统一遵照执行。

### 1. remark（AI 描述规范）
- **定位**：面向 AI 意图理解与开发者的精炼定位描述。
- **长度与结构**：1～2 句简洁概括，包含应用所属业务领域、服务对象与核心业务闭环（如：“面向制造企业的生产排程与车间派工系统，支持工单流转、物料齐套核销与质检追踪”）。
- **修订规则**：普通字段或视图修改无需变动 remark；仅当新增核心业务模块或应用整体定位升级时，微调更新以保持概括全貌。

### 2. desc 场景一：全新编写使用手册（新建应用 / 原手册为空 / 明确要求重写）

面向用户的业务操作指引，**必须使用原生 HTML + 行内 CSS 编写，禁止使用 Markdown**。当应用首次创建（build-app）、或者已有应用原手册为空、或者用户明确要求“重写手册”时，遵循本标准：

#### 推荐内容结构：
1. **开头**：1～2 句话介绍应用用途与解决的核心痛点；
2. **核心业务流转**：用简明步骤概述主流程（如：“客户报修 → 客服派单 → 工程师接单检修 → 备件消耗 → 客户验收结单”），明确角色协作路径；
3. **按角色分块**：为每个角色设立独立章节（`<div>` 或 `<h3>`），包含：
   - 角色名称（小标题）与一句话职责概述；
   - 核心操作步骤（日常高频操作与功能入口）；
   - 专属页面/工作台入口引导（如有）；
   - 审批流转要点（如有发起的审批或审批动作及结果说明）；
4. **关键状态说明**：解释核心单据的生命周期状态（状态名、触发方式是自动还是人工流转）；
5. **注意事项**：2～4 条容易踩坑的业务防呆提示（如操作先后约束、敏感数据撤回提醒）；
6. **AI 助手说明**（如有）：简要介绍智能助手可解答的问题或快捷指令。

#### 排版与暗黑模式适配铁律：
- **纯原生 HTML**：使用 `<h3>`、`<p>`、`<ul><li>`、`<div style="...">` 等标签。**严禁使用 Markdown 语法（如 `#`、`-`、`**`）**，前端会原样裸露；
- **文字颜色继承**：**严禁硬编码绝对字体颜色（如 `color:#000`、`color:#333`）**，必须让文字自动继承系统的明暗色主题；
- **高亮背景半透明**：高亮背景块**严禁使用纯浅色（如 `#f5f5f5`、`#fff`）**，必须使用半透明色彩点缀（如应用主题色的 10% 透明度：`background: rgba(48, 84, 235, 0.1); border-left: 3px solid #3054eb;`）；
- **去掉开发者视角**：严禁出现 ER 图、API 字段名、代码实现等技术性细节。

---

### 3. desc 场景二：已有使用手册的增量修订（自适应现有结构与风格）

在应用修订阶段（由 `app-navigation-revision-sub-agent` 执行），当已有应用已存在使用手册，用户要求修改文案、或因新增角色/表单/流程连带更新时，遵循以下核心原则：

1. **先读后改，自适应现有结构**：先调用 `get_app_info` 读取现有 `desc`。内容和结构可能是用户自己编写的（如按模块、按流程或简要段落），严禁强行套用场景一的 6 块模板推翻重写，应结合获取到的实际内容，在最合理的语义位置进行增补或修改。
2. **遵循已有风格**：观察现有文本的排版方式与行文习惯（如标签层级、列表形式、叙述语气），增补内容应主动模仿并遵循已有风格，做到自然融合。
3. **非侵入式最小修改**：仅做必要的手术式局部调整，未受影响的既有内容一律原样保留。
4. **底线约束**：保持原生 HTML 且严禁使用 Markdown 语法；文字不硬编码绝对颜色以适配暗黑模式；调用 `update_app` 时带齐 `name`、`icon` 等未修改属性防丢失。


## 应用项批量展示属性修改

已有工作表、页面、助手的导航名称/图标/显示模式及 remark/desc 使用 update_app_items，混合类型一次提交，无需 sectionId。remark 为开发者/AI 使用的简要备注，desc 为面向用户的说明，支持富文本；按目标选择，不默认同时改两者。只传批准属性：省略保持原值，name/icon 空字符串保持原值，remark/desc 空字符串清空内容。局部改写时按需读取并保留未改部分，明确替换或清空时不固定预读。工作表名称同步实体，页面/助手只改导航名称。应用和分组本身使用各自工具。逐项检查 updatedIds/skipped，只修正未成功项；displayType 独立写入需要回读 status，不能把外层成功当成显隐已生效。

## 导航分组删除

修订授权遵循 hap-revision-safety；以下为 delete_app_section 的层级与迁移语义。

| 当前分组 | delete_app_section 的处理 |
| --- | --- |
| 二级分组 | 直接删除，应用项自动回落父级一级分组；用户已明确其他去向时先完成授权移项，不询问默认回落位置。 |
| 唯一一级分组 | 不传 targetSectionId；后端清空分组名称呈现为无分组，按实际结果汇报。 |
| 存在其他一级分组，目标为空 | items 与 childSections 均为空才算空分组，直接删除。 |
| 存在其他一级分组，目标非空 | 将用户已指定/选择的目标，或唯一另一个一级分组，显式传 targetSectionId；多候选去向未决按共享安全规则处理。 |

不通过删除分组代替普通跨组移动，不删除组内工作表、页面或助手。
