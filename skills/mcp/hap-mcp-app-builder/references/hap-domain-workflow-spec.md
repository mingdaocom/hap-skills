# HAP 工作流执行易错规则

适用于普通工作流、自定义动作工作流的新建与修订。业务设计遵循 `hap-workflow-design-guide`；Build 的设计交接、Modify 的任务授权、结果包装和重试次数由各自执行器规定。

本规范保留跨节点业务约束及当前工具 Schema 未充分表达的易错点。已由实际入口清晰说明的参数规则不重复维护，历史缺陷修复后也不因曾经出错而永久保留；仍存在的部署差异或语义缺口注明适用条件。以下示例只展示易错结构，不替代完整请求，也不能直接复制占位 ID 执行。

## 一、参数以实际调用工具为准

- 参数名、必填项、类型、枚举、默认值和可用节点形态，以本次连接实际暴露的 MCP 工具 Schema、工具说明及真实回执为准。本规范不再维护第二份完整参数表；已证实的 Schema 与后端差异保留为例外提示，不能盲从错误默认值。
- 从实际入参位置沿 `$ref` / `oneOf` / `anyOf` 确认适用分支；不能仅凭同名 `$defs` 判断实际契约。不同环境的 Schema 不能混用，日期触发 `offset` 等参数不照抄旧示例。
- `create_process`、`batch_create_process_nodes`、`update_workflow_node` 的参数能力分别判断，不能把创建支持的字段直接带入修改。`config` 修改片段用原生 JSON 对象，不序列化为字符串。
- 复用已注入的工具定义、上下文和有效回执，只针对当前缺口查询，不增加固定的全量读文档、读取全应用或逐节点验证步骤。参数修正不能改变已确定的业务目标。

## 二、真实引用与作用域

- 表、业务字段、角色、视图和流程使用准确上下文或查询取得的真实 ID；同名按应用、所属表与目标范围消歧，不编造、不跨表照抄，不用字段别名代替业务字段 ID。选项显示名映射到真实 `key`。系统输出和流程参数按专用契约引用，不强制套用业务字段 ID 的长度规则。
- 普通新建流程优先复用 `create_process` 返回的 `processId` / `triggerAlias`，仅缺少必要信息时读取结构；自定义动作复用动作回执或上下文已绑定的关联流程 ID，从结构取得触发节点 `nodeId`，不另建普通流程或猜触发别名。定时流程没有天然触发记录，只有需要记录数据时才安排查询。
- `processId` 标识流程，不是节点 ID，禁止填入 `prevNode`、`parentNode`、`selectedNode` 或字段引用的 `node`。普通新建流程的第一个下游节点连接实际触发节点：按回执中的触发别名/节点 ID 引用，或按当前 Schema 省略 `prevNode` 使用默认连接；不能假定每个入口都返回 triggerNodeId。已有流程追加、插入或分支内首节点按真实拓扑连接，不把“本批第一项”一律接回触发器。
- 内部流程与父流程是独立作用域。子流程当前行来自 `sub_trigger`，审批块当前记录来自 `approval_start`，循环体内部触发别名为 `loop_trigger`；外层数据通过 `process.start.inputFields` 声明参数、父节点 `input` 按同一参数 ID 传值、内部 `process_variable` 引用这条链传入，不直接跨层引用节点。当前行字段不重复包装为外层参数。`sub_process.selectedNode` 须指向记录或记录集合节点，不能把单条记录上的多选人员/部门字段当集合拆成子流程，也不得将单条 `trigger` 套入 `parallel_each` 子流程伪造按人遍历；上游误拆的同文群发直接合并为主流程通知节点，禁止在真实流程中创建临时探针节点试探接口。循环体是否继承触发数据由 `inheritTrigger` 显式决定，其他外层传值方式以当前 Schema 为准。
- 工作流 Build/修订执行器按业务需要配置流程参数：用 `get_workflow_variables` 按需读取草稿，`update_workflow_variables` 保存完整集合，保留未改项、子项及已有 `fieldId`。新参数先保存取得真实 ID，再配置引用节点；恢复或保存失败后按当前定义接续，不重复提交无 ID 的新增项。
- `branch` 节点及其路径只用于控制流，不提供业务字段。连接参数与数据引用分别确定：即使 `prevNode` 指向分支节点，`left.node`、`right.node`、`selectedNode` 和模板取值仍须指向当前作用域内实际提供所需字段/记录的节点；不把分支或路径别名当数据源，也不假定所有操作节点都产出记录。
- 无需处理的分支保留空路径，正常汇合或自然结束，不为“无需处理/流程结束”添加 `terminate_process` 或其他占位节点。仅在业务明确需要提前终止当前流程、阻止后续执行时使用中止节点；空路径可能继续执行汇合后的节点，不能把“跳过本分支动作”误作“停止整个流程”。局部修订不顺带删除无关既有中止节点。
- 同批创建可用 `nodeAlias` 连接；跨批或已有节点复用真实 `nodeId`。读取父流程不展开块内 `process.nodes`；用块节点的 `config.process.processId` 按需读取内部结构，不能从父响应附带的内部节点推断连接关系。已知内部节点 ID 且只需详情时定向查询，复用未失效的结果。
- 应用角色与组织角色不同，人员、部门、职位等身份必须有真实 ID。工具支持某种身份不代表执行器能按名称查询；缺少必要引用时报告缺口，不能改用相近值、触发人或任意接收者。

### Lookup 的读取与来源取值

- 工作流 Agent 新建或修改节点取值时，不直接使用 Lookup 作为条件、收件人、模板变量或赋值来源，无论是否开启 `storeData`；通过查找/获取关联记录节点读取符合消费位置类型契约的真实来源字段。工作表展示仍可使用仅显示 Lookup，不为流程取值修改字段存储模式，也不顺带改造无关既有节点或流程。
- 沿 Lookup 的本表关联字段、目标表和来源字段确定取值链，复用已知字段详情；缺少配置时定向读取。来源字段仍是 Lookup 时继续解析，不能仅重新查询当前记录后继续引用同一个 Lookup，也不按字段名称或显示类型猜测。已有符合业务取值时点的上游来源记录直接复用；查询保留真实关联、单条/集合范围及缺失处理，不能用当前来源值冒充历史快照。无法取得满足要求的来源值时报告具体缺口，不改用任意记录或猜测值。
- 组装节点前一次检查所有引用位置，包括收件人、模板变量、条件与赋值来源；共享同一来源记录的字段复用同一查询，不逐字段重复查询。必要查询节点与消费节点按依赖同批创建，避免修好收件人后才发现变量仍引用不可用的 Lookup。例如手机号与奖品来自不同关联记录时，一次安排两个来源查询，再以查询结果中的手机号和奖品字段配置短信节点。

### 触发、参数与连接的定位提醒

| 场景 | 保留的执行要点 |
|---|---|
| 工作表事件 | 按业务确定事件、过滤和监听字段；下游回写触发表时检查退出或幂等条件，不能仅因设置了监听字段就认定不会循环 |
| 日期字段触发 | 明确基准日期、提前/延后方向和业务状态过滤；`offset` 按当前入口选择结构。声明 `unit/value` 的入口可用 `{"unit":"minute","value":-30}` 表达提前30分钟，不将未引用定义中的 `minutes` 写法混入 |
| 定时触发 | 明确时区、周期与开始时间，不照抄参考流程中过期的 `startTime`；数据统计时段与触发时刻分开确定 |
| 子流程输入 | 在 `config.process.start.inputFields` 声明 `fieldId/name/type`，父节点 `config.input[].field` 按同一参数 ID 传值，内部使用 `$process_variable-参数ID$`；不能把它写成 `$sub_trigger-参数ID$` |
| 同批与分支连接 | 当前创建接口中，分支路径首节点的 `prevNode` 指向所属 branch 节点，`parentNode` 指向对应路径；后续节点的 `prevNode` 指向前序节点，`parentNode` 保持路径归属。引用结构按当前 Schema，同批可用路径 alias，已有连接复用真实引用；路径不是数据源 |
| 审批块结果 | 父流程使用块的最终结果；内部审批人、意见等细节在内部作用域处理，不跨层直接读取内部节点 |
| 循环 | 按业务显式设置最大循环次数与出错处理，不依赖默认值；循环方式创建后不能切换，需要改变时局部替换节点。`use_existing` 共享已有循环体而非复制，修改内部节点会影响所有引用方 |

## 三、跨节点语义易错点

### 数据来源与输出

- 区分单条记录、记录集合、单字段值与模板正文；整条记录不能作为普通单值字段或正文。动态内容按工具支持的模板引用拼接，如 `$nodeAlias-fieldId$`，不捏造系统字段或输出名。
- `rollup`、`compute` 的 `number` / `dateDiff` 输出使用 `number_fx_id`，`dateOffset` 输出使用 `date_fx_id`；不要猜成 `number`、`total` 或工作表字段。`update_record` 不提供更新后的记录字段输出，下游确实需要写后值时重新查询。`update_process_variable` 不产出可按节点引用的字段，下游通过 `process_variable` 读取参数，模板内写作 `$process_variable-参数ID$`。当前节点不支持引用“距今天”类动态日期公式时，可用源日期与相同时间基准计算日期差，保留方向、单位和精度。
- 查找类写入节点的输出不同：`find_and_update` 输出单条记录，`dataVersion` 决定读到更新后（默认）还是更新前的值；`find_and_delete` 仅 `keepRecord: true` 时有记录输出；`find_and_batch_update` / `find_and_batch_delete` 不作为记录或集合数据源。`get_single_from_multiple` 的来源必须是上游多记录结果节点，不能指向单条查询或删除类节点。
- 查找类写入节点的筛选左侧属于目标表、`left.node` 指向当前节点自身，规则同查询节点。批量更新只能统一覆盖或清空，需要累加或逐行取值不同时改用子流程逐条更新。批量节点的 `filter` 在 Schema 中可省略，但不能因此扩大到整表，必须按已授权范围配置筛选与 `limit`。
- 汇总按实际 Schema 区分记录集合计数与工作表字段聚合，不混用两类来源。集合计数不能引用单条查询，也不能把分页或数量上限截断的集合当作全量；工具没有的统计模式不能自造，必要能力不足时报告缺口，不改统计口径。
- 条件操作符严格按照当前工具 Schema 的说明选择。关联字段不能当作普通文本值；关联字段按记录 ID 判断是否关联的条件见下文。为空判断不同于写入空值。条件组合保持平台支持的外层 OR、内层 AND 两层逻辑，不构造无法落库的多层嵌套；右值是否为数组按具体操作符契约处理，不套用统一格式。

### 多数据源动作的集合处理

- `recordScope: multiple` 的触发来源为记录集合；统一赋值/清空或删除时，用 `update_record` / `delete_record` 的 `selectedNode` 引用真实触发节点，不另查整表或任取一条代替选中集合。集合计数使用 `rollup(method: count)`；其他取值按消费位置的类型契约处理，不能把集合当单行字段。
- 合单时新建主单，通过指向来源表且支持多条的 Relation 字段，以 `kind: record` 引用触发集合；共享主单后逐条派生时，按子流程作用域规则传入主单，不虚构跨层引用。
- 自定义动作触发节点的单条/多条数据源在创建时固定，不能原地修改。切换需按动作领域规范删除并重建动作，再配置新关联流程；不能修改或替换旧触发节点实现切换。不把按钮已挂载当作流程已配置、已发布的证据。

### 关联记录获取

按设计中的查找范围和单条/集合语义选择节点，并核实关联字段的所属表与指向表；两边都有关联字段不代表两条路径等价，不能为修参扩大或缩小记录范围。

- **从来源记录的关联字段取数**：`get_related_record` 获取一条，`get_multiple_from_field` 获取集合。两者用 `selectedNode` 引用来源单条记录节点，`field` 使用该记录上的关联字段 ID；目标表由关联字段确定，不传 `worksheetId`。
- **在目标表按条件查询**：`get_single/get_multiple` 的 `worksheetId` 使用被查询的目标表 ID。目标表存在指向来源表的关联字段时，可查询该字段是否关联了来源记录：左侧引用当前查询节点的真实关联字段 ID，右侧以 `kind: field` 引用来源节点的 `rowid`，不传整条 `record` 或模板。示意式“目标表.关联字段 = 来源记录.rowid”的具体操作符严格按照当前 Schema 的 `Condition.op` 说明选择；不能只把错误条件左右交换，也不能把该关联字段指向的来源表当作查询目标表。
- **进一步筛选**：两个关联取数节点的 `filter` 可选，只筛选已关联的目标记录；左字段属于目标表，`left.node` 指向当前取数节点。没有额外筛选要求时省略。
- **落实选择规则**：将设计中的筛选、排序、取一条或多条、数量范围及无结果处理，按所选节点的实际 Schema 配置；不在单条与集合节点间照搬参数，需要全部记录时检查数量上限是否截断结果。
- **落实取数时点**：设计要求在中间修改前取数时，不能只调整节点顺序；`get_multiple_from_field` 默认在下游引用时取数，需要在到达节点时取数则使用 `execute: true`，并将节点放在相关修改前。其他节点按各自契约处理，不照搬此参数。
- **使用结果**：后续操作引用获取到的目标记录；需要工作表 ID 时使用该结果实际所属的目标表。集合逐条处理时使用子流程的当前记录，不把来源记录或整个集合当成单条目标。
- **条件左右值类型兼容与关联取数边界**：`Condition.right` 引用的动态字段类型须与 `Condition.left` 兼容（与界面「动态值」候选列表一致）：**文本/`rowid` 左值不收 `Relation`（关联记录）字段**（如 `left(目标表.rowid) = right(上游.Relation字段)` 会被直接拦截；顺着上游关联字段获取目标记录应直接使用 `get_related_record` 或 `get_multiple_from_field`）；**`Relation` 左值仅收指向同一张表的 `Relation` 字段或该数据源表记录节点的 `rowid`**。同时严禁将 `Relation` 字段放入 `$nodeAlias-fieldId$` 文本模板。确需更换已创建节点类型时，按第四章局部替换并更新下游引用。

### 值引用与过滤条件的必要示例

不同参数位置可能收窄允许的 `kind`，不能把 ValueRef 的全集套用到触发器、条件左侧或所有节点。以下示例使用当前 sandbox 的 `node` 与 `field`；节点选择位置使用 `selectedNode`，不要与 ValueRef 的记录值混用。

| 用途 | 结构或注意点 |
|---|---|
| 固定值 | `{"kind":"literal","value":100}`；值类型应与目标匹配，不能拿占位文字替换动态业务内容 |
| 上游字段 | `{"kind":"field","node":"source","field":"<真实字段ID>"}` |
| 系统时间/触发人赋值 | `{"kind":"systemField","field":"nowTime"}` / `triggeraid`；其他系统键按工具契约，不自造 `currentUser` 或 `date` |
| 记录值 | `{"kind":"record","node":"source"}`；仅用于接受记录值的位置，如关联字段赋值，不是正文或普通单值字段 |
| 动态正文 | `{"kind":"template","value":"结果：$summary-number_fx_id$"}`；自定义动作触发节点没有可用别名时，使用真实节点 ID 的模板引用 |
| 清空字段值 | 按写入接口使用 `op: clear` 或支持的 `kind: empty`，不要与过滤中的“为空”或配置补丁删键混淆 |

- `Condition.left` 使用 `kind: field`，提供所属节点与真实字段或受支持的节点输出引用；常量放在 `right`。节点不同，左侧的归属也不同：`get_single/get_multiple/get_related_record/get_multiple_from_field` 查询条件的左侧必须属于被查询工作表，`left.node` 指向当前查询节点自身，触发记录和其他上游值作为右侧动态值；`branch` 条件的左侧则引用上游记录字段或当前工具支持的计算、汇总输出，不能套用“只能是查询表物理字段”的限制。
- 工作流系统变量 `triggertime`、`nowTime`、`triggeraid` 按当前契约使用 `kind: systemField`，不能伪装成某条记录的 `kind: field`。在过滤条件中仅用于支持该类型的右侧位置，不因不能直接作为左值就把变量名填入左侧 `field`。`ctime`、`rowid` 等记录系统字段属于记录字段，按实际所属节点引用，不与工作流系统变量混淆。
- 修参必须保留时间口径：记录创建时间 `ctime`、流程触发时间 `triggertime`、当前时间 `nowTime` 不能互相替换来绕过校验。只有业务目标确实按记录创建时间判断时才使用 `ctime`；条件位置不支持原引用时，仅采用当前接口支持且语义等价的表达，不擅自改截止条件或捏造中间输出。
- 严格按照当前工具 Schema 中 `Condition.op` 的适用字段类型及语义说明选择操作符，并按 `Condition.right` 的要求构造右值；说明不足时核实契约，不凭名称或中文近义词猜测。右值是否为数组不决定查询返回条数。修正参数须保留原业务语义，不轮流试参，也不将记录 ID 匹配改成标题匹配来绕过校验。

### 汇总与计算参数组合

| 场景 | 需要配合的参数 | 不能混入的来源 |
|---|---|---|
| `rollup` 集合计数 | `method: count` + 指向多记录节点的 `selectedNode` | 不混入 `worksheetId` / `field`，不以单条查询充当集合 |
| `rollup` 字段聚合 | 当前支持的聚合方法 + `worksheetId` + `field`，筛选放在 `filter` | 不同时传集合计数的 `selectedNode`；`average` 与 `avg` 的接受及归一化按工具契约 |
| `compute` 数值 | `expression` 中引用真实字段或节点输出 | 不引用分支路径或更新节点的不存在输出 |
| `compute` 日期差 | 基准与结束时间、`outputUnit` | 输出为 `number_fx_id`，不是日期 |
| `compute` 日期偏移 | `inputTime` + `offsetExpression`，如 `+2d+8h` | 单位大小写有意义：`M` 月、`d` 天、`h` 小时、`m` 分钟，不写中文单位；输出为 `date_fx_id` |

- `rollup` 不照搬查询节点的 `ifEmpty`；聚合方式按当前入口对来源及字段类型的说明选择，不因旧入口缺陷排除当前已支持的模式。
- 计数与字段聚合可能属于不同节点子类型，不能因创建参数包含两种模式就认定原节点支持相互转换；按修改接口能力处理，不以恢复为由自动删除重建。

### 更新目标字段防护

- 按真实字段类型和记录值写入能力判断，不以界面是否可编辑代替。衍生类型 `30 Lookup`、`31 Formula`、`32 Concatenate`、`33 AutoNumber`、`37 Rollup`、`38 DateFormula`、`47 Barcode`、`53 FunctionFormula` 及纯布局/展示控件不能作为直接写入目标；未列出的类型也不自动视为可写。
- 必须改变衍生结果时，在原业务范围内修改可写来源字段；没有合法实现方式则保留草稿并报告缺口，不能改字段类型或删除必要更新来凑成可发布流程。
- 条码/二维码（Barcode）先核实实际生成配置：复用已有字段详情，缺少时优先用 `get_worksheet_field` 按已知表和字段 ID/别名查询，多个已知字段可同次读取；根据表达式中的实际引用按需补查来源字段，不按显示名称猜测，也不把它当作 Lookup 的 `sourceField`。仅需定位未知字段或核对跨字段关系时才读 `get_worksheet_structure`。需要改变编码内容且来源是可写字段时，将目标值写入该来源字段，由条码配置自动派生；来源为记录 ID、链接或其他衍生值时不能强行找一个字段写入。
- 已有配置和来源值足以满足目标，或本流程前置步骤会按原目标设置来源时，不再直接写条码字段，也不重复自赋值。此为原目标内的等价实现，无需预先声明 fallback 或额外确认；既有记录的来源值是否满足目标须有证据，不能仅凭字段存在认定完成。保留同一节点内其他必要且合法的更新，完成/已发送标记仍在相应操作成功后设置。省略冗余赋值或不再需要的节点时维持前后连接与引用，不删除业务步骤；仅真实来源仍无法解析、不可写且无等价实现，或存在其他必要缺口时保留草稿。

### 通知与人员

- 区分 PersonRef 接收者身份与 ValueRef 字段赋值：运行时触发人作为接收者使用 `triggerUser`；写入记录人员字段时使用系统字段 `triggeraid`。当前登录人不能替代运行时触发人或记录负责人。
- 站内通知的动态工作表字段应为人员（26）、部门（27）或组织角色（48）；人工节点的系统人员输出按专用契约引用。手机号、邮箱、普通文本和整条关联记录不能当作站内人员身份。
- 短信、邮件同样支持人员、部门、组织角色、职位、应用角色及触发人。人员 ID 可正常引用，即使查询返回的联系方式已脱敏；脱敏值不能用作固定号码或邮箱。
- 短信支持固定手机号、手机/文本字段，邮件支持固定邮箱、邮箱/文本字段；动态字段用 `kind=field`，按当前 Schema 对所在接收位置的字段类型要求配置，不套用站内通知的人员字段限制，也不将各位置允许的类型合并套用。短信文本字段需包含手机区号。
- 固定手机号使用 `kind=phone` + `phone`，仅用于 `send_sms.recipients`；固定邮箱使用 `kind=email` + `email`，仅用于 `send_email` 的 `recipients/cc/bcc`，每项一个真实地址。短信支持大陆号码及带 `+` 国家码的完整国际号码；港澳台/国际发送依赖组织集成相应短信服务，配置可保存不代表可送达。
- **短信模板选择**：Build 新建节点按方案正文传 `config.template`；Modify 新建默认同样处理，用户明确指定已有模板时按当前 appId 调 `get_workflow_sms_templates` 取得 templateId。已有节点仅改接收者或变量时沿用回读的 templateId；修改固定正文时创建新模板。查询失败或指定模板不存在时报告缺口，不猜 ID 或更换模板。
- **新建模板的签名**：按当前 appId 调 `get_sms_signatures`，复用主 Agent 交接或本会话同应用有效结果；仅业务 `success: true` 时从 `data` 原样选取签名。优先匹配用户指定值或明确品牌；无指定且唯一可用时直接采用，多项无唯一依据则返回候选供选择。查询失败、列表为空或指定值不可用时停止受影响的模板写入与发布。仅沿用 templateId 时不额外查询签名。
- **新建模板与变量**：签名、用途和完整正文按当前 Schema 填入 `template`；未注明用途时取行业通知，营销不伪装成通知。动态正文按占位符出现顺序绑定上游字段；切换或新建模板时一并传完整 bindings，无变量则传 `[]`，避免保留旧模板绑定。模板创建需要应用管理员权限，权限不足时报告缺口。
- 通知与邮件不互相套用配置。动态正文使用工具支持的模板，保留真实业务内容；不能为修复参数错误而替换成占位文字、减少接收范围；渠道适配按第四节保持通知效果。审批是否允许驳回等影响业务行为的设置，按已确定规则和工具默认值明确落实。
- 已知默认值差异：`approve.allowReject` 后端未传时允许驳回，即使 Schema 标为 `false` 也不能据此假设禁止驳回；业务明确要求不可驳回时显式传 `false`。

收件人映射仍保留必要示例：应用角色 `{"kind":"role","id":"<真实角色ID>"}`、固定人员 `{"kind":"user","id":"<真实人员ID>"}`、动态人员 `{"kind":"field","node":"source","field":"<真实人员字段ID>"}`；固定部门/职位/组织角色按对应真实身份配置，不用应用角色 ID 冒充。人工节点实际执行人引用 `executorid`，审批意见引用 `opinionSummary`，不自造内部后缀或把输出名猜成 `wfcuaids`、`opinion`。

站内通知的 `title` 在已有接口不产生标题效果，需要标题时写入 `content` 首行；邮件主题和正文按 `send_email` 自身字段配置。动态业务正文优先使用模板；接口接受固定字面量不代表可以把动态内容降级为固定文本，真正固定的文案则按当前工具支持的格式表达。

## 四、节点创建、修改与修复

- 以完成业务目标并交付可用流程为目标，发现设计与真实接口、字段或触发来源不一致时，先复用上下文和回执、定向补查缺失事实，主动完成等价修复，不因设计未列出替代写法就停止或要求额外授权。可调整节点类型与拆分组合、关联取值链、父子流程参数、可写来源，以及补齐默认参数与必要辅助节点；保持原记录范围、条件、时点、接收对象和业务结果。
- 通知只要求告知指定对象、未限定渠道时，可依据该对象真实联系方式与当前工具能力选择可用渠道，保持正文、时机与接收范围，遵守已有渠道、费用和隐私约束，并在结果中简述适配；不把缺少人员字段直接视为无法通知，也不把明确要求的站内通知任意改成短信。
- 未明确的常规参数优先复用应用已有规则；没有已有规则且不违背用户要求时，可按业务场景采用合理默认值（如普通图书续借 30 天），同一业务口径保持一致，并在结果中简述所采用的默认值，不因此停留草稿。用户明确规则不可覆盖，审批人等真实身份不可编造；字段说明中的疑似限制按实际配置与校验结果定位，不仅凭名称或说明认定无法实现。涉及其他流程已承担的效果，复用明确执行证据避免重复写入，不以一次查询未发现认定不存在。
- 围绕已授权业务目标，自主选择补建、原位修改、删除多余节点或局部重建。优先采用能保留正确配置和引用、改动较小的方式；节点类型、配置形态或连接无法原位修正时可删除重建，不必机械坚持 PATCH，也不因一次失败就重建整个下游。
- 创建按依赖和参数体积组织批次，复用已成功创建的流程与节点 ID。修复前后注意受影响的配置、连接和数据引用；删掉必要步骤不算修复，部分成功或未知结果按第六节处理。
- `update_workflow_node` 修改名称和业务配置，不支持更换节点类型或调整前后连接。补丁通常只需变化的键；形态键变化需要哪些配套参数、数组如何合并，以当前工具契约为准。整块 `config: null` 保留配置，对象内规范键的 `null` 才可能表示删除，不能混用。
- 回读可能缺项：`parentNode` 为空不等于分支归属丢失，`warnings` 或未完整返回的审批块配置也不能当成完整快照覆盖。复用上下文和回执，只有影响本次判断的信息不足时才定向补查；块内修改使用对应内部流程 ID。
- `batch_delete_process_nodes` 支持单个或多个节点，逐项执行、不回滚。根据 `results`、`deletedNodes`、`updatedNodes` 继续处理，保留无关节点与公共内部流程；替换节点后更新旧 ID/alias 的引用。删除和重建的范围、顺序由实际依赖决定，不预设删除全部下游或清理内部流程。
- 原目标内、影响未变的技术修复可直接继续。必要配置或引用无法保留、目标或风险实质扩大时，说明具体缺口并交回上游；恢复不自动扩大整个流程删除或任务外操作的授权。

## 五、交付与发布

- 按已确定的交付目标完成草稿或发布。发布前确认必要业务步骤和依赖已经落实，技术校验通过不等于业务完整；已授权发布且条件满足时继续执行，不因技术修参重复确认。
- 有待发布的内部流程时由内向外发布，再发布依赖它的父流程；复用未修改内部流程的有效发布证据。内部发布失败或结果未知时先处理该依赖，无关流程可继续。
- `publish_process` 自带校验，是否提前 `validate_process` 按执行器要求和改动复杂度判断，不机械重复校验。应用修订中，已授权发布、必要步骤及引用完整、无未解决问题的简单流程（含新建单条记录事件通知）直接发布，不固定先 `validate_process`；仅草稿交付、复杂拓扑/内部依赖改动或仍有待定位的配置问题时，先 `validate_process`。发布返回的校验结果已覆盖当前版本时直接复用，配置未变不再单独校验；发布失败按真实错误修复，不能删减必要步骤来通过校验。结合回执中的问题定位和真实状态自主修复，不仅凭一个错误码认定根因，也不因局部错误重跑整流。
- 以真实发布结果确认上线：`published`、`publishVersion` 与校验结果应一致；证据充分直接收口，不例行回读。结果不完整或未知时按第六节核实，分别报告已发布、草稿完成、未完成或未知，不能把仅创建或校验通过称为上线。

## 六、依据执行结果恢复

- 先判断实际执行到了哪里。明确未发出或确认未写入的调用可修正后重试，无需为证明未写入额外查询；部分成功则保留已完成项、真实 ID 和逐项结果，继续必要的修复，不整批重放。节点已创建不代表配置正确，修复方式仍按第四节选择。
- 超时、断连或返回不足时，先利用已有证据，必要时定向查询再决定下一步。`outputSchema` / `structuredContent` 返回校验失败不等于请求未执行；结果仍无法确定时如实报告未知，不靠重复写入试探。
- 根据报错阶段、实际参数和当前工具契约定位原因。类型错误应修正实际 JSON 类型；字段错误应核对记录字段、系统变量或节点输出的类别、所属节点/表及操作符。不要只换文案、交换左右值或删减业务内容来绕过错误。
- 新证据或有效参数修正可支持继续尝试；相同输入、相同错误没有进展时换诊断方式，不机械循环。Schema 与回执冲突时说明具体冲突，不能把一种写法失败等同于整项能力不支持；有契约依据且保持原目标的替代实现可自主采用。
- 发布非幂等，结果未知时核对已发布版本及时间，再判断是否仍需发布。成功回执充分就复用，不为修正最终汇报再次写入或发布；不通过实际触发业务流程来验证配置，也不把整个流程删除或弃稿当作恢复捷径。

## 工作流关闭与删除（仅修订）

授权遵循 hap-revision-safety；事实复用、验证与恢复遵循 hap-revision-execution。

- 关闭使用 `close_workflow`，保留配置和草稿，不处置运行实例，不声称已终止全部在途执行。
- 普通工作流整条删除使用 `delete_process(workflow_id)`；自定义动作触发的工作流不能直接删除，必须删除所属自定义动作，由动作执行器使用 `delete_custom_action` 处理。删除节点使用 `batch_delete_process_nodes`；弃稿按当前入口能力处理，不混用。不为删除先发布、关闭或弃稿，不自动删除目标引用的其他流程。
- 必要引用包括订阅、定时及审批/子流程等已知影响；工作表事件触发本身不能证明无影响。
- 整条删除仅在业务成功且 `data.processId` 匹配请求、`data.deleted: true` 时完成；缺失或矛盾回执按未知结果处理。已删除流程不再调用结构、校验或发布工具。
